# v9.3 — LLM-구동 I/O 워크로드 (구현 완료)

> 상태: **구현 완료** (`pc_sampling_fuzzer_v9.3.py`, FUZZER_VERSION=9.3.0). 아래는 최종 확정 설계 = 구현 반영본.
> 착수 전 초기 설계 대비 **단순화**됨: 별도 FFM burst-score/포화감지/fast-slow분류/디바이스상대예산 폐기 →
> **FFM = 파생 telemetry 필드 1개**로 흡수, 포화는 **단일 FFM 필드 patience(상승 후 정체)**로 축약. §4/§5 참조.

## 0. 동기
- SSD 펌웨어의 깊은 로직(FTL 매핑 / GC / wear leveling / fragmentation)은 **단일 명령이 아니라 누적 I/O 패턴이 내부 상태를 threshold로 밀 때** 발동한다(= 사용자 논문 **SDF-Fuzz** 논지).
- 현재 LLM은 coverage-gap 프레이밍 때문에 **Read/Write를 안 만듦**(블라인드가 IO 코드를 이미 덮어 gap이 admin으로 몰림). 그런데 SSD는 Read/Write가 주(主)이고, 그로 인한 내부 알고리즘을 탐색해야 한다.
- I/O는 **명령 수천 개**가 있어야 상태를 민다. LLM에게 JSON으로 6개 명령 받는 건 무의미.

## 1. 핵심 아이디어
LLM이 **raw 명령이 아니라 "상태 구동 워크로드 레시피(descriptor)"** 를 내고, fuzzer가 **증폭 실행 → 텔레메트리 델타(FFM)로 평가 → corpus 저장·재활용**. I/O를 **state 축**에서 탐색하되 **fuzzing 본질(랜덤·포화 기반)을 유지**.

## 2. 변경 요약 (v9.2 대비)

| 영역 | 기존(v9.2) | v9.3 변경 |
|---|---|---|
| LLM task | 3개(new_group_seeds/sequences/corpus_eval) | **+`io_patterns`**(가중 라운드로빈, 기존 무변경) |
| LLM 출력 | seed(CDW)/sequence(명령 리스트) | io_patterns는 **워크로드 descriptor**(compact 레시피) |
| LLM 입력(grounding) | OACS/ONCS, SC digest, coverage-gap | **+텔레메트리 `{name,value,desc}`** → LLM이 의미로 판단(제품 무관) |
| I/O 실행 | io_workload 엔진 **고정 config 패턴** 블록 | **LLM descriptor 증폭 실행, chunk 단위, saturation/안전캡 종료** |
| 평가 | state delta(매 100명령), C2 score | **+FFM(텔레메트리 델타 측정)** — state-cov 1차, edge-cov 2차 |

**그대로(안 버림):** 기존 3 task, 명령 레벨 fuzzing/변이/커버리지, 블라인드 퍼저, 안전 가드, edge-cov. io_patterns는 가중치 추가라 기존 탐색 대체 안 함.

## 3. `io_patterns` task — descriptor
LLM 출력(예):
```json
{"io_workload": {
   "pattern": "overwrite_churn",   // seq_fill | random | hot_cold | fragment | read_disturb
   "lba_start": 0, "lba_span": 100000,
   "block_size": 8,                // NLB
   "hot_fraction": 0.1,            // hot/cold 분할
   "read_ratio": 0.3,
   "direction": "drive free_blocks down toward GC"   // semantic 방향(하드 목표 아님)
}}
```
- fuzzer가 이걸 **수천 개 실제 Write/Read로 전개**. LLM 출력은 작게 유지.
- LLM 값어치 = "지금 상태에서 어떤 워크로드가 GC/wear를 미나"를 텔레메트리+desc로 판단.
- 검증: pattern enum, LBA/block 범위 clamp(안전).

## 4. 증폭 실행 + 조기 종료 (fuzzing 본질 유지) — `_run_llm_workload_burst`
**하드코딩 목표 없음.** 버스트 = descriptor 패턴을 block 단위로 반복 발송, **FFM(단일 파생 필드) 상승 후 정체 시 조기 종료**.
```
snap0 = FFM 관측
ffm_max = ffm0; stale=0; armed=False
while blocks < BURST_BLOCKS_MAX:                 # 천장(config, 예 50 block=5000 I/O)
    SNAP_BLOCKS(예:5) block 실행                   # 매 명령 PC샘플 → edge-cov 자동 크레딧
    if wall-time cap 초과: break                  # 안전 backstop
    FFM 관측(state capture 비싸므로 이 주기로만)
    if FFM > ffm_max:  ffm_max=FFM; stale=0; armed=True   # 새 최고 압력 → 계속
    elif armed:        stale += 1; if stale>=PATIENCE_K: break   # 올랐다 정체 = 평형 도달 → 종료
    # FFM 이 한 번도 안 오르면(armed=False) 천장까지 감 (느린/무효 구분불가 → 최대 기회)
FFM_델타 = ffm_max - ffm0                          # 도달한 peak 압력 = 워크로드 효과
```
- **왜 armed-after-rise**: FFM 이 안 움직일 때 조기 종료하면 "느린 필드"를 "무효"로 오판. → **한 번이라도 오른 뒤에만** patience 발동. 오르다 정체(GC 평형)면 종료(마모 절약), 안 오르면 천장까지.
- **왜 SNAP_BLOCKS 주기**: `state_monitor.capture()`(smart+vendor+security 서브프로세스)는 비쌈 → 매 block 금지, 수 block마다 1회.
- **예측 가능**: 버스트 = 항상 `[PATIENCE_K·SNAP_BLOCKS, BURST_BLOCKS_MAX]` block 범위. 무한/즉시종료 없음.
- **fuzzing 성질 유지**: (a) 패턴 안 LBA/block 랜덤 변이, (b) 버스트 사이 명령-레벨 fuzzing 지속(io_patterns는 가중 task 하나), (c) 도달한 worst-case 상태 = 발판. LLM=방향(semantic), fuzzer=탐색-until-정체.

## 5. FFM = 파생 telemetry 필드 (`source:'derived'`, `fn:'frag_pressure'`)
**별도 "burst score" 개념 폐기.** FFM 을 **관측 필드**로 만들어 기존 파이프라인(`delta`/`state_cov_map`/버킷/LLM `{value,desc}` 되먹임)이 자동 처리. `capture()` 가 raw 필드를 읽은 뒤 계산해 주입.

**공식(0..100 정규화 가중평균, 존재 항의 가중치로 재정규화):**
| 항(kind) | 입력 필드 | 정규화 | 기본 w |
|---|---|---|---|
| fill (inv_pct) | `sec_free_blocks_pct` | (100−v)/100 = GC 압력(핵심) | 0.40 |
| skew | `df_max_pe_cycles`,`df_avg_pe_cycles` | (max−avg)/max(avg,1) = wear 편중 | 0.25 |
| slc (pct) | `sec_slc_pct_used` | v/100 | 0.15 |
| sys (pct) | `sec_sys_data_pct_used` | v/100 | 0.10 |
| end (pct) | `percent_used` | min(v,100)/100 | 0.10 |

```
FFM = round(100 · Σ(w·term) / Σ(w over 존재 항))
```
- **제품 무관**: 입력 필드가 raw 에 없는 항은 자동 제외 + **존재 항 가중치로 재정규화** → 유효 0..100 유지. 신제품에 df_* 없으면(예: p9) skew 항 빠지고 나머지로 재정규화(검증: r8 5항=75, p9 4항 동일압력=77). 필드 없으면 안 봄 = config 표 관리 불필요.
- **활성 카운터는 FFM에 안 섞음**(무한 카운터 스케일 함정): `sec_patrol_relocated/read_reclaim/refresh_counts/wear_level_count` 는 **각자 기존 telemetry 필드**로 델타 관측(EVENT 신호). FFM = bounded 압력 STATE 지수.
- FFM 델타가 `state_cov_map` 새 버킷 넘으면 state-cov 크레딧 자동(기존 C2 재활용). LLM 되먹임(§6)에도 그대로 노출.

## 6. 워크로드 corpus (저장·재활용 = amortization)
- 효과적 워크로드(FFM 델타 큰 것)를 **descriptor + FFM-EMA score**로 저장(수천 명령 아님, replay 시 재증폭).
- **replay**(재증폭 → 깊은 상태 재도달, C2 state replay의 확장) + **mutate**(파라미터 변이 → 워크로드 공간 탐색).
- 기존 메커니즘 그대로: score/energy(FFM-EMA), dedup, staleness(상태 못 미는 워크로드 퇴출), favored(유일 상태 영역 미는 워크로드 보존).
- 재현 뉘앙스: 효과는 시작 상태 의존 → score는 EMA(완벽 결정론 아님, 정상).
- **왜 필요**: LLM은 좋은 워크로드 한 번 제안 → corpus가 재활용/파생(LLM 재호출 없이). KernelGPT/ChatAFL "durable artifact" 원칙.

## 7. DRP 미채택 (정정)
- DRP(사용자 SDF-Fuzz)는 **점진 단조 진행을 "새 상태"로 보상** = worst-case 유도용. 하지만:
  - 노이즈 카운터(WriteUncorrectable 에러 카운트 등)에 쓰면 **flood 증폭**(역효과).
  - I/O 워크로드 saturation 판정은 **단순 per-chunk driving-변수 델타**로 충분.
- **결론: v9.3에서 DRP 미사용. 상태 버킷팅 현행 유지.** WriteUncorrectable flood는 **v9.2의 패턴 dedupe + staleness**로 이미 처리.
- (DRP는 향후 "threshold-driving 변수 전용 state-coverage 정밀화"가 필요해지면 그때 선택적 검토.)

## 9. 리스크 / 주의
