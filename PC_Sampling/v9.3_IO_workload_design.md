# v9.3 (계획) — LLM-구동 I/O 워크로드 설계

> 상태: **설계 문서(미구현)**. 구현 착수 전 고정용. 현재 최신 코드 = `pc_sampling_fuzzer_v9.2.py`.

## 0. 동기
- SSD 펌웨어의 깊은 로직(FTL 매핑 / GC / wear leveling / fragmentation)은 **단일 명령이 아니라 누적 I/O 패턴이 내부 상태를 threshold로 밀 때** 발동한다(= 사용자 논문 **SDF-Fuzz** 논지).
- 현재 LLM은 coverage-gap 프레이밍 때문에 **Read/Write를 안 만듦**(블라인드가 IO 코드를 이미 덮어 gap이 admin으로 몰림). 그런데 SSD는 Read/Write가 주(主)이고, 그로 인한 내부 알고리즘을 탐색해야 한다.
- I/O는 **명령 수천 개**가 있어야 상태를 민다. LLM에게 JSON으로 6개 명령 받는 건 무의미.

## 1. 핵심 아이디어
LLM이 **raw 명령이 아니라 "상태 구동 워크로드 레시피(descriptor)"** 를 내고, fuzzer가 **증폭 실행 → 텔레메트리 델타(FFM)로 평가 → corpus 저장·재활용**. I/O를 **state 축**에서 탐색하되 **fuzzing 본질(랜덤·포화 기반)을 유지**.

## 2. 변경 요약 (v9.2 대비)

| 영역 | 기존(v9.2) | v9.3 변경 |
|---|---|---|
| LLM task | 3개(new_group_seeds/sequences/corpus_eval) | **+`io_patterns`**(가중 라운드로빈, 기존 무변경) |
| LLM 출력 | seed(CDW)/sequence(명령 리스트) | io_patterns는 **워크로드 descriptor**(compact 레시피) |
| LLM 입력(grounding) | OACS/ONCS, SC digest, coverage-gap | **+텔레메트리 `{name,value,desc}`** → LLM이 의미로 판단(제품 무관) |
| I/O 실행 | io_workload 엔진 **고정 config 패턴** 블록 | **LLM descriptor 증폭 실행, chunk 단위, saturation/안전캡 종료** |
| 평가 | state delta(매 100명령), C2 score | **+FFM(텔레메트리 델타 측정)** — state-cov 1차, edge-cov 2차 |
| 재활용 | Seed/SeqSeed, state_corpus(raw 시퀀스) | **+워크로드 corpus**(descriptor+FFM-EMA) replay/mutate |
| 피드백 | SC digest/accept-CDW/SC-depth(명령 레벨) | **+텔레메트리 델타 되먹임**(I/O판 repair 루프) |
| 상태 버킷팅 | CSFuzz power-of-2(`_adaptive_bucket`) | **현행 유지**(아래 §7 DRP 미채택) |

**그대로(안 버림):** 기존 3 task, 명령 레벨 fuzzing/변이/커버리지, 블라인드 퍼저, 안전 가드, edge-cov. io_patterns는 가중치 추가라 기존 탐색 대체 안 함.

## 3. `io_patterns` task — descriptor
LLM 출력(예):
```json
{"io_workload": {
   "pattern": "overwrite_churn",   // seq_fill | random | hot_cold | fragment | read_disturb
   "lba_start": 0, "lba_span": 100000,
   "block_size": 8,                // NLB
   "hot_fraction": 0.1,            // hot/cold 분할
   "read_ratio": 0.3,
   "direction": "drive free_blocks down toward GC"   // semantic 방향(하드 목표 아님)
}}
```
- fuzzer가 이걸 **수천 개 실제 Write/Read로 전개**. LLM 출력은 작게 유지.
- LLM 값어치 = "지금 상태에서 어떤 워크로드가 GC/wear를 미나"를 텔레메트리+desc로 판단.
- 검증: pattern enum, LBA/block 범위 clamp(안전).

## 4. 증폭 실행 + 적응형 종료 (fuzzing 본질 유지)
**하드코딩 목표 없음. 포화(diminishing returns) 기반 종료** — AFL energy schedule과 동형.
```
반복(chunk = 예: 500 I/O):
  snapshot(before-chunk)
  chunk 실행(패턴 안에서 LBA/block 랜덤 변이)
  snapshot(after-chunk) → chunk 델타
  if driving 변수(free_blocks 등)가 아직 worst-case로 이동 → 계속
  elif plateau(N chunk 동안 driving 변수 변화 ~0) → 종료(diminishing)
  elif 안전캡(write budget / max chunk / wall-time)   → 종료
누적 델타(시작~끝) = 워크로드 점수(FFM)
```
- 개수 결정 = **per-chunk 진전**(끝나기 전에 알 수 있음). 최종 의미 = **누적 델타**. 같은 신호의 두 해상도.
- **fuzzing 성질 유지**: (a) 워크로드 패턴/파라미터 랜덤 변이, (b) 명령 레벨 fuzzing 지속, (c) 도달한 worst-case 상태 = 발판. LLM은 방향(semantic), fuzzer는 탐색-until-포화.
- plateau 판정은 **단순 per-chunk driving-변수 델타**로 충분(DRP 불필요, §7).

## 5. FFM (측정자 — 타겟 아님)
현재 telemetry(state_fields)로 바로 구성 가능. **"FFM=X 달성" 같은 하드 타겟 없음.** 세 용도: ① 워크로드 점수, ② saturation 감지(FFM 델타 plateau→종료), ③ LLM 되먹임.

**활용 필드(현 state_fields에 존재):**
- **압력(worst-case 진행)**: `sec_free_blocks_pct`(핵심, GC-trigger), `sec_slc_pct_used`, `percent_used`.
- **wear 편중(fragmentation)**: `df_max_pe_cycles − df_avg_pe_cycles` 갭, `sec_wear_level_count`, `sec_system_max_ec`.
- **유지보수 실제 발동**: `sec_patrol_relocated`, `sec_read_reclaim`, `sec_refresh_counts`.
- **제품 무관성**: 필드명/오프셋이 제품별로 달라도 **LLM에 `{값+설명(desc)}`을 주면 의미로 판단** → FFM 가중치 하드코딩 회피.

## 6. 워크로드 corpus (저장·재활용 = amortization)
- 효과적 워크로드(FFM 델타 큰 것)를 **descriptor + FFM-EMA score**로 저장(수천 명령 아님, replay 시 재증폭).
- **replay**(재증폭 → 깊은 상태 재도달, C2 state replay의 확장) + **mutate**(파라미터 변이 → 워크로드 공간 탐색).
- 기존 메커니즘 그대로: score/energy(FFM-EMA), dedup, staleness(상태 못 미는 워크로드 퇴출), favored(유일 상태 영역 미는 워크로드 보존).
- 재현 뉘앙스: 효과는 시작 상태 의존 → score는 EMA(완벽 결정론 아님, 정상).
- **왜 필요**: LLM은 좋은 워크로드 한 번 제안 → corpus가 재활용/파생(LLM 재호출 없이). KernelGPT/ChatAFL "durable artifact" 원칙.

## 7. DRP 미채택 (정정)
- DRP(사용자 SDF-Fuzz)는 **점진 단조 진행을 "새 상태"로 보상** = worst-case 유도용. 하지만:
  - 노이즈 카운터(WriteUncorrectable 에러 카운트 등)에 쓰면 **flood 증폭**(역효과).
  - I/O 워크로드 saturation 판정은 **단순 per-chunk driving-변수 델타**로 충분.
- **결론: v9.3에서 DRP 미사용. 상태 버킷팅 현행 유지.** WriteUncorrectable flood는 **v9.2의 패턴 dedupe + staleness**로 이미 처리.
- (DRP는 향후 "threshold-driving 변수 전용 state-coverage 정밀화"가 필요해지면 그때 선택적 검토.)

## 8. 구현 단계 (v9.3, 순차 + 단계별 검증)
1. **`io_patterns` task + descriptor + 증폭 실행**(포화/안전캡) — 핵심 신기능. (기존 io_workload 엔진 확장 재활용.)
2. **FFM 측정**(워크로드 전후 델타, 위 필드 가중) + saturation 종료 신호.
3. **텔레메트리 되먹임 루프**(델타 → LLM, 제품 무관 `{값+desc}`).
4. **워크로드 corpus**(descriptor 저장 + replay/mutate + FFM-EMA).

## 9. 리스크 / 주의
- **증폭 I/O = 실물 PE cycle 소모** → 워크로드당 **안전 write 캡 필수**(현 io_workload limit 재활용).
- io_patterns 가중치 과하면 admin 탐색 감소 → **weight로 균형**(기본 2, 과하면 낮춤).
- 전체가 커서 **v9.3로 분리** + 단계별 A/B(edge-cov/state-cov 추이) 권장.

## 10. 연결(기존 자산 재활용)
- io_workload 엔진(증폭 I/O), state monitor(텔레메트리 델타), C2 score/replay(상태 재현·보상), RAG_TASK_WEIGHTS(task 균형), 안전 가드/write limit — 전부 재활용. 신규 코드 최소화.
