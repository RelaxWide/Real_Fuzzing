# RAG service의 `LLM 호출 실패: 'hits'` 진단

## 확인한 내용

`processing <id> (task 프롬프트 ...자)`는 bridge 요청을 읽은 뒤 온라인 guide를
호출하기 직전의 로그다. 이어지는 `LLM 호출 실패`는 `srag_llm_guide.py`의
`generate_rag_response()` 또는 그 하위 코드에서 전달된 예외를 서비스가 출력한 것이다.
LLM 모델 API까지 호출되었다는 뜻은 아니다.

기존 서비스는 예외를 `str(exc)`로만 출력했다. `KeyError('hits')`가 발생하면
정확히 `'hits'`만 보인다. 다만 문자열 하나만으로 예외 타입을 확정할 수 없으며,
검색 응답의 키 누락인지, 문자열 템플릿 처리인지도 traceback 없이는 구분할 수 없다.

온라인 guide는 저장소 밖에 배포하는 파일이며 이번 작업 환경에서 찾지 못했다.
따라서 **실제 `hits` 실패 원인은 아직 미확정**이다. 최근 변경과의 인과관계도
확정하지 않았다. 누락된 키를 빈 결과로 바꾸는 우회는 적용하지 않았다.

## 적용 및 다음 로그

온라인 LLM PC에서 실행 중인 **서비스 파일**을 저장소의
`PC_Sampling/rag/srag_llm_service.py`로 교체하고 서비스를 다시 시작한다.
실제 guide와 같은 폴더에 두며, 기존에 수정한 bridge 경로/모듈 설정이 있으면 유지한다.
퍼징 PC의 v10.2 파일만 갱신하면 온라인 서비스에는 반영되지 않는다.

수정 서비스는 다음을 출력한다.

- 예외 종류와 메시지, 마지막 발생 파일·줄 번호·함수명.
- 해당 예외의 traceback(지역변수 및 요청/응답 본문 덤프는 추가하지 않음).
- 재시도 실패 시 같은 요약을 bridge 오류 응답에도 포함.

서비스의 기존 reload 후 1회 재시도는 유지한다. 모든 실패를 연결 끊김으로
단정하던 안내만 수정했다. 퍼저의 실패 횟수 설정은 변경하지 않았다.

다음 실패의 traceback에서 온라인 guide를 가리키는 부분을 확인한다.
검색 응답 접근 줄이라면 그 요청의 HTTP 상태와 응답 구조를 확인하고,
문자열 format 줄이라면 템플릿 치환 키와 리터럴 중괄호를 확인해야 한다.
어느 쪽인지 확인하기 전에 인증/서버/프롬프트 길이를 원인으로 단정하지 않는다.

## 검증

장치/외부 서버 없이 서비스의 실제 함수로 3개 회귀 테스트 통과:
`KeyError('hits')`의 guide 파일·줄 번호 및 traceback 전달,
일시적 연결 오류 후 재시도 성공, 첫 호출 성공 시 reload 미실행.
실제 온라인 guide 및 검색/LLM 서버를 통한 성공 복구는 미검증이다.
