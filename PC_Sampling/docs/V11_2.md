# 1. PM preflight

## 문제 (v11.1 까지)

| | 내용 |
|---|---|
| 멈춤 | PM preflight 의 nvme 호출(SetFeatures PS, get-feature, id-ctrl)이 `subprocess.run(timeout)`. timeout 이 나면 kill 뒤 `process.wait()` 를 하는데, 무응답 장치에서 ioctl 이 커널 안(D 상태)에 묶이면 그 wait 가 끝나지 않는다. `0d26edf` 의 Pre-flight 멈춤과 같은 원인 |
| 실패 무시 | `_pm_preflight_check` 는 항상 True. 복귀 실패·NVMe 무응답이어도 다음 조합으로 넘어가 깨진 장치로 퍼징까지 들어갔다. S1/S2 도 결과를 아무도 보지 않았다 |

## 변경

- PM 경로 nvme 호출은 `_pm_nvme_run` → `_run_nvme_state_cmd`(timeout 이면 프로세스를 버리고 rc=-1).
  무응답이면 `_pm_unresponsive` 에 남긴다. 대상: `_pm_set_state`, `_pm_verify_combo` 의 get-feature,
  `_init_ps_settle`, preflight 의 id-ctrl 폴백, S1/S2 생존 확인. 메인 루프의 PM 명령도 같은 함수를 쓰므로
  거기서도 멈추지 않고 실패로 돌아온다
- nvme-cli `--timeout` 은 **일부러 더하지 않았다** — 커널이 명령을 abort 하면 컨트롤러 리셋으로 현상이 사라진다.
  (`_pm_set_state` 의 기존 `--timeout=3000` 은 그대로)
- 판정

| 상황 | 처리 |
|---|---|
| 진입 실패만(복귀·NVMe 정상) | 예전처럼 FAIL 표시 후 다음 조합 |
| 복귀 실패(PS0+L0+D0 미복귀, PS MISMATCH 포함) | 중단 |
| 복귀 뒤 NVMe 실패(get-feature·id-ctrl 모두 실패) | 중단 |
| 어느 단계든 nvme 무응답(D 상태) | 그 자리에서 중단 — 이후 PM·NVMe 명령을 더 보내지 않는다 |
| S1/S2: 항목 적용 뒤 id-ctrl 무응답·실패 | 중단. 쓰기 실패·cap 없음 같은 항목 실패는 예전처럼 계속 |

- 중단 = `_pm_preflight_fail`: 복구 POR/리셋 없이 현상 보존. `_timeout_crash` 를 세워 `finally` 가 기존 timeout
  crash 와 똑같이 SMART 조회·APST/keepalive/커널 timeout 복원을 건너뛰고 PC 관측을 한다.
  증거는 `crashes/crash_<ts>/`: `pm_preflight.json`(kind·stage·target·reason·조합별 결과),
  `replay_pm_preflight.sh`(PM 진입/복귀가 든 `_cmd_history`), 로그, dmesg, 제품 설정에 따른 JLink/UFAS/DebugTool 덤프
- `run()` 은 False 면 그 자리에서 return(정리 범위 안). `--allow-no-openocd` PM 시험 모드도 중단한다

```
[PM-Preflight] 실패 — 캠페인 중단 (복구 POR/리셋 없이 현상 보존)
[PM-Preflight]   대상: PS4+L1.2+D0  단계: 복귀
[PM-Preflight]   원인: nvme admin-passthru 가 5s 안에 응답하지 않음
```

## 한계

- 무응답 판정 기준은 호출마다 5s(기존 값). 커널 쪽에서는 그 명령이 `nvme_core.admin_timeout` 까지 살아 있다.
  PM preflight 는 `_configure_nvme_timeouts` 보다 앞이라 보통 기본 60s 이고, 그 뒤 커널이 컨트롤러를 리셋할 수 있다
- 버려진 D 상태 nvme 프로세스는 남는다(종료 불가). 장치가 돌아오면 함께 끝난다
- 진입 자체가 실제로 됐는지(L-state 실측·PMU 전류)는 판정에 넣지 않았다 — 지원되는 PM 만 시험하므로 필요 없다고 판단

시험: `tests/test_v11_2_pm_preflight.py` 16건. 중단 조건·무응답 기록·run 연결을 하나씩 되돌리면 실패하는 것을 확인했다.

# 2. coverage_growth — LLM 돌파 표시

v11.1 의 아래 그래프(LLM ÷ mutation 효율 배수)는 누적·최근 추세라 "mutation 이 한참 못 뚫던 것을 LLM 이
뚫었다"는 순간이 안 보였다. 위 그래프에 그 지점을 표시한다.

**돌파 정의** (`_llm_breakthroughs`, 입력은 기존 `_cov_share_hist` — 새 수집 없음)
- mutation 정체 = mutation 계보가 새 BB 를 못 찾는 동안 **mutation 이 실행한 자기 명령 수**(corpus 에서 골라
  실행한 cmd·seq). LLM 이 명령을 다 가져가 mutation 이 기회가 없던 구간은 길어 보여도 정체가 아니다
- 기준 = `max(breakthrough_min_mut_cmds(1000), breakthrough_gap_factor(5) × mutation 평소 발견 간격 중앙값)`.
  제품·단계마다 발견 속도가 달라 절대값 하나로는 못 맞춰서 그 실행의 평소 간격에 비례시켰다
- 정체가 기준 이상일 때 LLM 계보가 새 BB 를 찾은 스냅샷 = 돌파. mutation 이 다시 찾을 때까지 LLM 이 찾은 BB 를
  합산한다. 같은 100명령 스냅샷 안에 mutation 도 찾았으면 순서를 알 수 없어 돌파로 세지 않는다

**표시**
- 위: 정체 구간 연한 주황 음영, 돌파 지점 BB 곡선 위 ★, 정체가 긴 상위 `breakthrough_labels`(3)개에
  `LLM +N BB / mutation 0 new BB for 12.2k cmds (22m, 54x usual gap)` 주석. 범례에 건수·합계·기준
- 아래: 같은 x 에 점선
- 범례를 왼쪽 위 → 왼쪽 아래(누적 면적 위)로 옮겼다. 왼쪽 위는 초반 곡선과 주석을 가렸다
- 로그: `[StatGraph] LLM 돌파 N건 (mutation 정체 기준 …명령, LLM +M BB)`

**해석 주의** — 한 실행 안의 표시다. "그 시점에 mutation 은 못 찾고 LLM 은 찾았다"까지이고, LLM 이 없었으면
mutation 이 결국 못 찾았을 것이라는 근거는 아니다(그건 `compare_runs.py` 의 ON/OFF 비교 몫).

시험: `tests/test_v11_2_breakthrough.py` 9건(판정 7·차트 2). 판정·정체 단위·적응 기준·합산·표시를 하나씩 되돌리면 실패하는 것을 확인했다.

# 3. io_patterns 응답 모양 (11.2.1)

`FUZZER_VERSION` 11.2.0 → **11.2.1**(같은 파일). 출력 폴더가 `pc_sampling_v11.2.1` 로 바뀌고, 실행 기록의 `version` 이
달라 `compare_runs.py` 가 수정 전후 실행을 한 그룹으로 섞지 않는다.

**증상** — rag_bridge 백엔드에서 `task=io_patterns 응답에 ['io_workload'] 중 아무것도 없음`. 응답은
`{"seeds": [], "sequences": [], "evaluations": []}`, 기록의 `diagnostics` 는 `{}`.

**원인** — 브리지는 스키마(`response_format`)가 없어 프롬프트 문구만으로 모양이 정해진다(진단도 안 준다). 그런데
- 시스템 프롬프트(브리지에서는 user 앞에 붙는다)가 키를 seeds/sequences/evaluations 로만 적고 그 모양만 보여 줬다
- 앞에 grounding 블록(과거 시드 few-shot `{"command":...}`, 명령 제안 지시)이 붙었다
- 학습 evidence 블록이 **맨 뒤**에 붙어 "target_id 를 seed·sequence·generator 에" 로 끝났다
- io_workload 는 중간의 "a single object with key io_workload" 한 줄뿐이었다

**변경**
- 시스템 프롬프트: 최상위 키에 `io_workload` 를 **추가**하고 "task 가 요구한 키만" 으로. 키별 모양에 io_workload 모양 추가.
  seeds·sequences·evaluations 모양은 **그대로** — 그 task 들은 필드 구조를 여기서만 얻는다
- io_patterns: grounding 블록을 싣지 않는다(상태를 바꾸지 않는 텍스트라 다른 task 는 영향 없음). 마지막에 완성된 출력
  모양 `{"io_workload": {"pattern": ..., ...}}` 와 "다른 키 금지"
- io_patterns: 학습 evidence 블록을 붙이지 않는다(`NVMeFuzzer._llm_build_learning_request` override — 공유 모듈
  `llm_learning.py` 는 그대로라 이전 버전 동작 불변). io_workload 는 target_id 를 쓰지 않아 잃는 정보가 없다

**따라오는 동작 변화**
- io_patterns 요청이 학습 대상 함수의 제시 횟수(offered)를 더 이상 올리지 않는다 — 대상 순번은 다른 task 로만 돈다
  (예전엔 쓰이지도 않는 대상을 '제시했다' 고 셌다)
- io_patterns 의 검색 질의(`[RAG-QUERY]`, vLLM 검색)는 학습 대상의 호출 명령 대신 커버리지 공백 명령으로 만든다 —
  학습을 끈 상태와 같은 경로
- 시스템 프롬프트 문구는 모든 task 가 공유하므로 다른 task 의 LLM 응답도 약간 달라질 수 있다
- vLLM 스키마·파서·응답 검증·교정 재요청·장치 경로는 그대로

시험: `tests/test_v11_2_prompt_shape.py` 9건. override·grounding 제외·마지막 모양·시스템 프롬프트 키/모양을 하나씩
되돌리면 실패하는 것을 확인했다.

# 4. replay 가 PM 동작을 preflight 와 같게 (11.2.1)

**증상** — PM preflight 에서 복귀 실패(`SET=OK RESTORE=FAIL NVMe=FAIL`)가 난 조합이 replay 에서는 정상.

**원인** — replay 가 실제 동작이 아니라 요약 항목(`pcie_state` 등)에서 setpci 를 **따로 다시 만들었다.** 그래서
- L1 ASPM enable 순서: preflight 는 EP→RP, replay 는 RP→EP
- Clock PM(ECPM): preflight 는 CPM 지원과 무관하게 켬, replay 는 CPM 지원 시만
- L1 진입 전 CLKREQ# assert(PMU)·L1SS·LTR 해제, 전역 ASPM 정책 쓰기(`powersave` ↔ 원래 값): replay 에 없음
- 진입 검증(목표 상태에서 `nvme get-feature`, `lspci -vv`, setpci 읽기, PMU 전류): replay 에 없음
- 대기: preflight 는 PS settle(0.5~2s+)·L1 settle 등, replay 는 고정 0.1s

**변경**
- 저수준 동작을 실행하는 helper 가 실행 내용·rc·시각을 이력에 `kind='op'` 로 남긴다:
  `_setpci_read`/`_setpci_write`, `_pmu_clkreq_assert`/`_deassert`, ASPM 정책 쓰기(`_op_sysfs_write`),
  검증용 PMU 전류·`lspci`(`_op_run`), 검증용 nvme get-feature·id-ctrl(`_pm_nvme_run`). PS SetFeatures 는 기존 `pm`
  항목에 시각만 더한다. D-state·S1/S2 교란·L1.2 경로도 같은 helper 를 거치므로 모두 잡힌다
- replay 는 op 를 **기록 순서 그대로** 실행하고, 시각이 있는 항목 사이는 **기록된 간격만큼 sleep**(상한 30s —
  기동 대기 같은 긴 공백만 자른다). op 가 있으면 `pcie_state`·`pcie_pm_bit`·`clkreq` 요약 항목은 setpci 를 다시
  만들지 않고 주석만 남긴다. 시작 부분에서 ASPM 정책을 퍼저 시작 때 값으로 맞춘다
- 이력(`_CmdHistory`): 명령은 예전처럼 최근 100개, 그 사이 op 는 함께(전체 5000 상한). 밀려난 명령 바로 뒤의 op 는
  남은 첫 명령 직전 동작이라 남긴다. state corpus 스냅샷에는 op 를 넣지 않는다(메모리)
- python3 스크립트(PMU) 경로는 절대 경로로 기록 — replay 는 crash 폴더로 cd 해서 돈다

**여전히 다른 것 (스크립트로 못 맞추거나 일부러 둔 것)**
- nvme 명령 timeout: replay 는 기존대로 `--timeout=3600000`(현상 보존용). preflight PS 전환은 3s
- 폴링 대기(config 응답 대기 등)는 **기록된 읽기 횟수·간격**으로 재생한다. 조건을 보고 기다리지는 않는다
- 디버거(OpenOCD/J-Link) 연결·디버그 전원: replay 는 만들지 않는다. 같은 조건이 필요하면 디버거를 연결한 채 실행
- 명령 실행 시간 자체는 그 시점 장치에 따라 다르다(간격만 맞춘다)
- 이 기록은 11.2.1 이후 실행부터. 그 전 crash 폴더의 replay 는 예전 방식 그대로

시험: `tests/test_v11_2_replay_ops.py` 10건 — 실제 `_set_pcie_l_state(L1→L0)` 를 돌려 **실행한 setpci·PMU 명령 목록과
replay 의 실행 줄 목록이 순서까지 같은지** 대조, 검증 명령·PS 명령·간격·상한·요약 항목 비재구성·이력 상한, `bash -n`.
기록 지점·간격 sleep·요약 항목 처리·경로 절대화를 하나씩 되돌리면 실패하는 것을 확인했다.

# 5. BM9K1 — PM 동작 중 디버그 세션 분리 (11.2.1)

**현상** — BM9K1 에서 `--pm` 이면 PM preflight 의 PS4+L0+D0 진입 검증 get-feature 가 무응답 → 장치 소실.
`--no-jlink`(디버그 연결 없음)면 정상, `--pm` 없이 디버거만 붙이면 정상, 퍼저를 끄고(J-Link 닫힘) replay 를 돌리면 정상.
→ 관측은 **디버거 세션과 PM(PS4)의 상호작용**을 가리킨다. 구체적 원인(디버그 전원 요청·링크 활동·인증 상태 중 무엇인지)은
실기 확인 전이다. 양산 환경에 없는 조건이라 불량 판정은 디버거 없이 재현될 때로 미루고, 퍼저는 이 상호작용을 피한다.

**변경** — 제품 설정 `pm_detach_sampler: true`(BM9K1 만). `--no-jlink` 면 꺼진다. **모든 PM 동작**을 디버그 세션을 닫고 한다.
- PM preflight: 전체를 세션을 닫은 채 돈다(시작 전 1회 분리, S1/S2 까지 끝나고 1회 재연결)
- 메인 루프 combo 슬롯
  - 동작 상태 조합(PS0~2 이면서 L0/L1·D0): 분리 → 진입 → 재연결 → **그 상태로 퍼징을 잇는다**(예전과 같은 의미)
  - 깊은 상태(PS3/PS4, 또는 D3·L1.2): 분리 → 진입 → PS settle 만큼 머묾 → **직전 동작 상태로 복귀** → 재연결.
    L1.2·D3 는 기존 nonop 복귀 뒤 PS 가 깊으면 동작 PS 로도 내린다(L1.2 복귀는 PS 를 그대로 둔다)
  - 진입 실패: 기존 규칙대로 nonop 복귀를 부르지 않고 원래 PS 로만 돌려놓는다
  - 복귀 목표(`_prev_op_combo`)는 깊은 상태가 아닌 조합만. timeout 기준 PS(`_prev_op_ps`)는 원래 규칙(PS 3/4 제외)
- 메인 루프 forced_idle 슬롯(APST 자율 PS3→PS4): 분리 → APST 짧은 ITPT → 대기 → APST 끄기 → PS0 → 재연결
- 메인 루프 pcie_bit(S1)·clkreq(S2) 슬롯: 분리 → 교란 → 재연결
- 분리는 퍼저 종료 때와 같은 `sampler.close()`, 재연결은 기존 장애 복구 경로 `sampler._reconnect()`(재시도·backoff)
- 재연결 실패 = 기존 샘플러 장애와 같이 `_sampler_recovery_failed` → 메인 루프 중단

**재연결 전 안전 조건 (코드 리뷰 반영)** — 깊은 상태를 벗어났다는 것이 **확인된 뒤에만** 다시 붙인다.
- 복귀 결과를 명시적으로 받는다: `_set_power_combo` / `_pm_set_state` 반환값, `_nonop_restore_checked()`(기존
  `_nonop_restore` 는 실패해도 목표 조합을 돌려줘 성공을 알 수 없었다 — 기존 호출부용 래퍼로 남김), 그리고 그 사이 nvme 무응답
  (`_pm_unresponsive`). 하나라도 실패·무응답이면 **다시 붙이지 않고** `PM-Detach` 로 현상 보존·증거 수집·중단
  (`crashes/crash_<ts>/pm_preflight.json`, kind=`PM-Detach`). `_current_combo`/`_current_ps` 는 성공 확인 뒤에만 복귀 목표로 갱신
- forced_idle: `_apst_disable()` 은 캠페인 시작 때 APST 가 원래 꺼져 있었으면(`_orig_apst_cdw11 == 0`) 해제를 **생략**했다 →
  짧은 APST 를 켠 뒤 끄지 않고 재연결해 다시 PS3/PS4 로 내려갈 수 있었다. 이제 `force=True` 로 끄고 get-feature 0x0C 로
  AE=0 을 **다시 읽어 확인**한다. `_apst_disable()` 은 set-feature 성공 여부를 돌려준다(sysfs `power/control=on` fallback 은
  런타임 PM 해제지 APST 해제가 아니라 반환값에서 뺐다). set-feature 는 D 상태 안전 실행으로 바꿨다
- 분리 확인: `sampler.close()` 뒤 J-Link 핸들이 실제로 닫혔는지(`session.lk.jl is None`) 본다. 닫히지 않았으면 그 PM 동작을
  건너뛰고 다시 연결한다. PM preflight 에서 닫히지 않으면 디버거가 붙은 채 PM 을 돌 수 없으므로 중단한다
- S1/S2: 교란 함수의 `False` 는 '건너뜀(cap 없음 등)'과 '복귀 실패(PMCSR D0 readback 등)'가 섞여 있다. `False` 면 id-ctrl 로
  장치 응답을 확인해 응답이 없으면 다시 붙이지 않고 보존·중단, 응답하면 경고 후 재연결
- 종료 후 PC 관측(`_read_bm9k1_monitor_pc`)은 닫힌 세션이면 읽기를 시도하지 않는다(보존 중단 뒤 다시 붙이지 않음)
- (2차 리뷰) forced_idle 의 APST **활성화**도 D 상태 안전 경로(`_pm_nvme_run`)로 보낸다. 예전엔 `subprocess.run(timeout=5)` 라 무응답을
  남기지 않아 해제·PS0 복귀 확인 없이 재연결했다. 거절(rc≠0, APST 안 켜짐)은 건너뛰고 붙이고, 무응답(완료 여부 미상)은 추가 명령 없이 보존·중단
- (2차 리뷰) 조합 진입이 무응답이면 PS 복귀 명령을 보내지 않고 바로 보존한다. 응답이 있었던 진입 실패에만 복귀를 시도한다

**한계** — 확인하는 것은 **J-Link 세션(핸들) 닫힘**이다. 디버그 전원 요청(DP CTRL/STAT CDBG/CSYS PWRUPREQ)을 해제하거나 확인하는
코드는 없다. 세션을 닫으면 PC 접근은 멈추지만, 이것만으로 '디버그 전원' 가설을 검증했다고 보지 않는다.

**동작 차이**
- PM 동작 중의 PC 는 수집하지 않는다(PM-Cov 없음). 동작 상태 조합에 머무는 동안의 퍼징 명령 PC 는 예전처럼 수집한다
- 깊은 상태(PS3/PS4·D3·L1.2)에 머문 채 퍼징 명령을 보내지 않는다(예전엔 PS3/PS4 에 둔 채 다음 명령이 장치를 깨웠다).
  깊은 상태 탈출은 복귀 명령으로만 시험된다
- PM 슬롯마다(100명령마다) 재연결 시간이 든다. 로그: `[PM-Detach] 재연결 OK — combo … x.xs [누적 N회, 재연결 평균 …s, 재인증 M회]`
  (처음 3회와 재인증이 있었던 회만 WARNING, 나머지 INFO). **재인증 횟수가 0 이 아니면 알려 줄 것** — 재연결 비용·빈도를 다시 봐야 한다

시험: `tests/test_v11_2_pm_detach.py` 32건(리뷰 반영 전 15건) — 동작 상태 조합 유지, 깊은 상태 복귀 순서, PS1+L1.2 처리와 복귀 목표, L1.2 의 PS 복귀,
진입 실패 시 nonop 복귀 생략, 재연결 실패 중단, 재인증 집계, forced_idle, pcie_bit·clkreq, BM9K1 만 켜짐, `--no-jlink` 무시,
preflight 감싸기, 메인 루프 연결 + 리뷰 회귀: 원래 APST=0 에서도 실제 해제 명령·재확인, APST 재확인 불일치·해제 실패 시 보존,
PS4→동작 상태·L1.2 링크·L1.2 PS·D3 복귀 실패와 무응답 시 재연결 안 함, nonop 복귀 결과 노출, close 실패 시 PM 생략,
S1 False + 장치 무응답 시 보존, sysfs fallback 이 APST 성공으로 둔갑하지 않음, 닫힌 세션 PC 관측 생략 + 2차 리뷰: 실제 APST 활성화
함수 timeout → 추가 명령 없이 보존·거절 → 건너뛰고 재연결, 진입 무응답 → PS 명령 없이 보존.
리뷰 지적 지점 10곳을 하나씩 되돌리면 모두 실패하는 것을 확인. 재연결 전 안전 조건을 이루는 `_apst_disable`·nonop 복귀는
mock 없이 실제 함수를 돌린다(nvme·setpci 경계만 가짜).
실기 미검증 — 첫 실행에서 PM preflight 가 끝까지 지나가는지와 재연결 시간·재인증 횟수를 확인할 것.

# 6. BM9K1 — 샘플링이 명령 실행 속도에 영향을 주지 않게 (11.2.1)

## 문제
BM9K1 이 `--no-jlink` 일 때보다 훨씬 느렸다. PM9M1 은 그렇지 않다. `RiscvPcsrSampler._sampling_worker` 가 PM9M1 워커와 달랐다.
- `stop_event` 를 **버스트(약 205~307회 읽기) 경계에서만** 봤다. 명령이 1ms 만에 끝나도 `stop_sampling()` 이 진행 중인 버스트를
  끝까지(읽기 한 번 = J-Link USB 왕복 한 번) 기다렸다. PM9M1 은 샘플마다 본다
- 세션 붕괴를 감지하면 워커가 **명령 실행 도중** 재오픈·재인증(`session.recover`)을 했다. APST 도 끄지 않은 채였다

## 변경
- **명령이 끝나면 즉시 멈춤**: `PcsrSession.burst(..., stop=)` 가 읽기마다 파이썬 콜백으로 `stop_event` 를 본다. DAP 접근·지연을
  더하지 않는다(실측 폴링 제약은 DRW 읽기 사이의 지연·재시도 금지다). 멈추면 진행 중이던 읽기 하나로 끝난다.
  끊긴 SBA 읽기 하나는 다음 `pin`/`read_word` 의 `sba_unpin` 이 정리한다
  - 오버레이 확인 코어는 명령 종료로 끊긴 버스트도 끝 bank 확인 읽기를 하고 bank 가 같으면 샘플을 살린다. 처음엔 확인을
    생략하고 버렸는데, 빠른 명령은 거의 모든 창이 버스트 도중 끝나 H 코어 샘플이 거의 전부 버려져 edge-cov 가 사라졌다(실기)
  - 명령 종료로 끊긴 버스트가 전부 읽기 실패여도 단발로는 transport 로 판정하지 않는다(일시 실패로 재연결이 돌지 않게). 대신 **창을 넘겨**
    연속 횟수를 세고 3회(`_STOPPED_FAIL_LIMIT`)면 transport 로 판정한다 — 짧은 명령만 이어지면 모든 버스트가 끊겨 장애가 영영 안 잡히기
    때문이다. 읽기가 하나라도 성공한 버스트가 오면 0
  - 빈 버스트(pin 실패) 연속 횟수(`_EMPTY_BURST_LIMIT` 8)도 같은 이유로 창을 넘겨 세고, pin 이 성공한 버스트에서 0 으로 돌린다
- **붕괴 복구는 명령 뒤에**: `_maybe_recover` 는 `openocd_error` 만 세우고 샘플링을 멈춘다(`stop=collapse`). 명령이 끝난 뒤
  `_stop_sampling_checked` 가 APST·keepalive 를 끄고 재초기화/재연결한다. `[Stats]` 의 `collapse: N(복구 M)` 은 `collapse: N` 으로 바뀐다

**포화 조기 종료는 넣지 않는다** — 명령이 끝나면 읽기가 멈추므로 실행 속도와 무관하다. 줄이는 건 명령 실행 중의 동시 읽기
(창당 최대 `max_samples_per_run` 500회)뿐인데, 그것이 명령에 영향을 준다는 근거는 없고 커버리지 손실은 확실하다.

## 동작 차이
- 명령이 끝난 뒤의 샘플(후처리 구간)은 수집하지 않는다. 빠른 명령은 창당 샘플 수가 줄어든다 — 커버리지가 계속 부족하면
  명령 종료 뒤 고정 샘플 수(꼬리)를 두는 설정을 검토
- 명령 실행 중의 SBA 폴링은 그대로다(커버리지 측정 자체)

시험: `tests/test_v11_2_sampler_stop.py` 13건 — 진짜 `PcsrSession.burst`·워커에 DAP 읽기만 가짜. 멈춘 뒤 추가 읽기 없음(메인 스레드
stop 포함), 오버레이 끝 확인 생략·폐기, bank 읽기 직후 stop, 끊긴 버스트 transport 미판정·전체 실패는 판정, 붕괴 시 워커 재연결 없음·
전부 무효 창은 붕괴로 넘김, 포화 없이 max_samples 까지, 짧은 창 연속 전부 실패 → transport, 성공 읽기면 리셋,
pin 실패 창 넘겨 누적, pin 성공(오버레이 폐기 포함)이면 리셋. device AST 기준선(`tests/fixtures/v10_2_device_ast.json`)의 v11.2
`RiscvPcsrSampler` override 를 이유와 함께 갱신.
실기 미검증 — `--no-jlink` 대비 실행 속도, transport/빈 버스트 비율을 확인할 것.

## 코어 전환·bank 읽기를 짧은 경로로 (78e7eea 이후)
명령 종료 즉시 멈춤을 넣은 뒤에도 `--no-jlink` 대비 약 1/10 이었다. 창 시작의 SBA 준비는 멈출 수 없는데, 코어 전환
(`sba_unpin`→`sba_pin`)과 코어 0(H, 가중치 8/14)의 버스트마다 앞뒤 오버레이 bank 읽기(`read_word` = unpin + `_sba_read`, 뒤
버스트에서 다시 `sba_pin`)가 검증형 쓰기(`mem_write32` = USB 왕복 7)로 처음부터 다시 설정해 첫 PC 읽기 전에 수십 번 왕복했다.
빠른 명령은 그 준비가 끝날 때까지 기다리고도 샘플을 거의 못 얻었다.

- `sjtag_unlock.sba_retarget`: 핀 상태(FIFO 모드·CSW·TAR=sbdata0)를 유지한 채 **sbaddress0 만** 바꾼다. 모드·CSW 재설정은 생략하지만
  **검증은 `mem_write32` 수준을 유지한다**: TAR 을 쓸 때마다 되읽기, 진행 중 read 완료 대기(에러·모드 불일치면 실패), sbaddress0 쓰기
  (readonaddr 로 새 주소 read 시작) 뒤 posted write 완료·DP sticky 확인(RDBUFF·CTRL/STAT)과 sbaddress0 되읽기 == 새 주소, 그 read 의
  완료·무에러 확인, TAR=sbdata0 고정·되읽기. 실패한 단계 뒤로는 DRW 를 건드리지 않는다. 재시도·에러 클리어는 하지 않는다 —
  **실패하면 예전 전체 경로**(`sba_unpin`→`sba_pin` / `_sba_read`)가 에러 클리어부터 다시 한다
  - (리뷰) 처음 구현은 마지막 TAR 되읽기만 해서, TAR→sbaddress0 쓰기나 주소 쓰기가 조용히 실패하면 **이전 코어의 PC 를 새 코어 값으로**
    받고 fast 성공으로 집계했다(커버리지·LLM 피드백 오염). 위 검증을 넣어 고쳤다
- `PcsrSession.pin`(코어 전환)과 `read_word`(bank 읽기)가 먼저 짧은 경로를 쓴다. bank 읽기는 짧은 경로로 주소를 프로브로 바꾼 뒤 DRW
  한 번으로 읽고, 다음 pin 이 짧은 경로로 PCSR 로 되돌린다. 버스트 핫루프는 그대로
- 모형 기준 USB 왕복(검증 포함): 코어 전환 40 → 16, bank 읽기 56 → 17, bank 뒤 PCSR 복귀 23 → 18 (`tests/test_v11_2_sba_retarget.py`의 SBA 모형 — 실기 수치 아님)
- 끄기: BM9K1 `riscv.sample_plan.fast_switch: false` (예전 경로). `[Stats]` 에 `sw: fast N/fail M/full K` — fail 은 짧은 경로가 실패해 전체
  경로로 되돌린 횟수(재연결을 넘겨 누적). **fail 이 계속 늘면 알려 줄 것**

시험: `tests/test_v11_2_sba_retarget.py` 19건 — 실제 `MemDap`·`sba_pin/unpin/retarget`·`PcsrSession` 아래에 SBA 레지스터 모형(readonaddr/
readondata, busy, sbbusyerror, DP sticky, 쓰기 유실 주입). 새 코어 값 읽기·왕복 수, 버스트 직후 진행 중 read 대기, 프로브 읽기 후 PCSR 복귀,
꺼짐 = 예전 경로, sberror·FIFO 꺼짐·전송 실패·예외 시 전체 경로로 복귀 + 리뷰 주입: TAR→sbaddress0 유실, 주소 쓰기 유실(+STICKYERR /
조용히), TAR→sbcs·TAR→sbdata0 유실 → 이전 코어 값이 섞이지 않고 전체 경로로 새 코어를 읽음, 각 단계 실패 뒤 DRW 접근 없음.
13곳 되돌리면 모두 실패. 모형은 sbdata0 연속 읽기를 항상 완료로 본다(실기 가정) — 실기 미검증.

## 리뷰 반영 — 준비 단계 중단, 시간 분해, PM 뒤 가벼운 재연결
- **버스트 전 준비도 명령이 끝나면 중단**: 시작 bank 읽기와 pin(짧은 경로)이 USB 왕복 하나 단위로 멈춤 요청을 본다.
  첫 PC 읽기 전에 명령이 끝났으면 그 창에서 얻을 샘플이 없기 때문이다. 검증은 빼지 않는다 — 주소를 쓴 뒤에는
  posted write·sticky·되읽기까지 마치고 멈춘다. 중단되면 세션 상태를 '미상'으로 표시해 다음 전환이 1단계부터 재확인
  (실패 시 전체 경로)하게 하고, 명령 종료 뒤에는 전체 경로(수십 왕복)로 이어 붙지 않는다. 중단된 준비는 pin 실패로 세지 않는다.
  **버스트 뒤 끝 bank 확인은 중단하지 않는다**(끊긴 버스트의 H 코어 샘플을 살리는 단계 — 위 ovl-drop 77% 원인 수정)
- **[Timing] (100회마다)**: 실행당 평균 — 전송(명령 실행) / 종료 대기 / 기타(회계·변이·PM 동작) / SBA 준비·PC 읽기(워커,
  명령과 겹침; 준비 중단 횟수) / PM 재연결 횟수·평균. 전송 경로 기준 코드(`_V101Fuzzer._send_nvme_command`)는 그대로 두고
  `NVMeFuzzer` 에서 감싸 잰다
- **PM 분리 뒤 가벼운 재연결(`RiscvPcsrSampler.reattach`)**: 전체 재연결은 settle 0.5s, 코어마다 PC 200개 ELF 정합성 게이트,
  오버레이 프로브 재검사를 매번 했다. PM 분리는 같은 펌웨어·같은 전원 구간이라 코어↔ELF 대응이 바뀌지 않으므로 세션 열기(인증
  확인 포함) + 핀 + 코어마다 32샘플 확인(유효 PC 가 첫 연결 때 검증한 실행 범위 안 ≥ gate_threshold)만 한다. 유효 PC 가 하나도
  없거나 범위 밖이 많으면 실패 → 기존 전체 재연결. `[PM-Detach] 재연결 OK … (가벼운 경로 N)` 으로 집계
- 리뷰의 포화 조기 종료는 넣지 않았다(앞 절 근거 — 명령 실행 속도와 무관, 커버리지 손실 확실). burst_len 축소는 같은 샘플
  예산에서 전환·bank 조회가 늘어 우선순위를 낮췄다

- (리뷰) **중단과 실제 실패를 구분**: 종료 신호만 보고 pin 실패를 '중단'으로 접으면, 짧은 명령에서 실제 SBA 장애가 겹칠 때 영영
  세지지 않았다(20창 연속 샘플 0, 오류 0 재현). 세션이 마지막 준비 결과(`last_setup` = ok/aborted/fail)를 남기고, 버스트는 실제로
  그만둔 경우만 'aborted' 로 보고한다. 종료와 겹친 실제 실패(시작 bank 읽기 포함)는 창을 넘겨 준비 실패로 센다(한도 8 → pin_fail)
- (리뷰) [Timing] 기준값을 측정 시작 때 잡는다 — 예전엔 첫 출력의 SBA·PM 값이 0/누락
- (리뷰) 가벼운 재연결의 범위 검사를 **코어별로** — 합산하면 정상 코어 표본이 한 코어의 범위 밖 PC 를 가렸다. WFI 코어는 그대로 허용

# 7. PM 슬롯 주기 — 배수를 건너뛰어도 다음 반복에서 (11.2.1)
예전 조건 `executions % pm_rotate_interval == 0` 은 **반복 시작 때 실행 수가 정확히 배수일 때만** PM 슬롯을 돌렸다.
- 한 반복에 여러 명령을 실행하는 시퀀스·det 묶음·LLM 시퀀스가 배수를 건너뛰거나(98 → 103), 그 반복이 워크로드로 빠지면
  (`continue`) 그 주기 PM 이 통째로 빠졌다. 시퀀스 비율이 높을수록 PM 이 드물어졌다
- 반대로 가드 차단처럼 실행 수가 늘지 않는 반복이 배수에서 거듭되면 PM 이 연달아 돌 수 있었다

지금은 `_pm_take_slot()`: 실행 수가 **예정 이상**이면 그 반복에서 돌고, 다음 예정을 그때부터 `pm_rotate_interval` 뒤로
잡는다. 밀린 만큼 연달아 돌지 않고, 같은 실행 수에서 다시 돌지 않는다. 첫 반복에서 한 번 도는 것은 예전과 같다.
LLM 학습 준비 중(`_learning_setup_active`)에는 여전히 건너뛰고, 끝나면 다음 반복에서 돈다.

시험: `tests/test_v11_2_pm_schedule.py` 5건(주기·배수 건너뜀·반복당 7개씩도 주기마다·연달아/중복 없음·메인 루프 연결). 3가지 변형으로 되돌리면 실패.
