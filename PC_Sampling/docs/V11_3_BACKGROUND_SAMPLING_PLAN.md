# v11.3 계획 — BM9K1 상시 백그라운드 샘플링

2026-10-15 작성, 같은 날 설계 리뷰 4회·구현 리뷰 3회 반영(§9). 같은 날 **v11.3.0 으로 구현했다(§10)** — 실기 검증 전이라 기본값은 꺼짐이다.
구현이 계획과 다르게 간 부분은 §10.2 에 적었다.
이 문서의 수치(USB 왕복 횟수)는 코드에서 센 값이고, 왕복 1회의 실제 시간과 실행 속도는 실기에서 재지 않았다.

대상: `pc_sampling_fuzzer_v11.2.py`(FUZZER_VERSION 11.2.1) → v11.3. BM9K1(RISC-V, `riscv_pcsr` 샘플러)만 바꾸고,
PM9M1·BM9H1·P7·P9 는 지금 방식을 그대로 둔다. BM9K1 도 **설정으로 켜는 opt-in** 이며, 끄면 v11.2 창 방식으로 바로 돌아간다(§2.4).

---

## 1. 왜 필요한가

### 1.1 증상과 실측

- BM9K1 은 디버거를 붙이면(`--no-jlink` 없이) 붙이지 않았을 때보다 명령 실행 속도(exec/s)가 크게 떨어졌다.
  v11.2.1 이전 측정으로 약 1/10 수준이었다. PM9M1 은 같은 퍼저 코드에서 디버거를 붙여도 정상 속도다.
- v11.2.1(명령이 끝나면 샘플링 즉시 정지)의 `[Timing]` 실측(2026-10-15)은 다음과 같다. 값은 전송 1건 평균이다.

| 항목 | 초반 | 후반 |
|---|---|---|
| 전송(명령 실행 — `start_sampling` + nvme-cli 완료까지) | 7.7ms | 111~116ms |
| 종료 대기(샘플링 정지·join) | 0.7ms | 0.3~0.6ms |
| 기타(회계·변이) | 1.9ms | 2.1~2.8ms |
| SBA 준비 · PC 읽기(워커, 명령과 겹침) | 4.6ms · **1.0ms** | 36.7ms · 64.2ms |
| 준비 중단(명령이 준비 중에 끝남) | 1952건 중 **981회** | 3~4회 |

이 실측이 말하는 것:

1. **v11.2.1 뒤에는 샘플링이 명령을 기다리게 하는 시간이 작다**(종료 대기 1ms 미만). "명령마다 정지·대기" 비용은 이미 대부분 없어졌다.
   따라서 v11.3 으로 바꿔도 **exec/s 가 크게 늘 것이라고 기대하지 않는다.**
2. 대신 **짧은 명령의 커버리지가 거의 안 잡힌다.** 초반 명령은 평균 7.7ms 인데, 워커는 그중 4.6ms 를 준비(bank 읽기·주소 이동)에 쓰고
   실제 PC 읽기는 1.0ms(샘플 몇 개)뿐이었다. 절반은 준비 도중 명령이 끝나 **샘플 0개**였다.
   명령마다 샘플링을 새로 세우는 구조에서는 준비 비용이 명령 시간 안에 들어가므로, 명령이 짧을수록 관측이 사라진다.
3. 후반 속도 저하는 샘플링 대기가 아니라 **명령 실행 시간 자체가 15배 늘어난 것**이다(§8).

### 1.1.1 그래서 v11.3 의 목적

**명령 실행과 커버리지 측정을 서로 다른 흐름으로 떼어 놓는 것**이다. 워커는 명령과 무관하게 계속 PC 를 읽고(준비는 명령 시간 밖에서 미리 끝나 있다),
메인은 명령만 보낸다. 명령 시간 구간에 들어온 샘플을 그 명령의 것으로 나눠 준다.

- 짧은 명령도 그 구간에 워커가 이미 읽고 있던 샘플을 받는다(준비 중단으로 0개가 되지 않는다).
- 명령 종료 처리가 샘플링 상태(정지·join·끝 bank 확인)에 묶이지 않는다. 남은 종료 대기 1ms 미만도 없어진다.
- 샘플링 쪽의 느린 경로(전체 경로 폴링, 재연결 준비)가 명령 전송을 막지 않는다.

### 1.2 "비침습인데 왜 명령이 느려지나"

BM9K1 의 PC 샘플링은 코어를 **멈추지(halt) 않는다.** SBA(System Bus Access)로 PCSR 레지스터를 읽기만 한다.
그렇다고 장치에 영향이 전혀 없다고 단정할 수는 없다. SBA 읽기는 SoC 시스템 버스를 쓰고, 그동안 디버그 전원 영역이 켜져 있으며,
호스트에서는 J-Link USB 트래픽이 계속된다. 다만 **이 문서가 다루는 속도 저하는 장치보다 호스트 퍼저 루프 쪽에서 생긴다.**
exec/s 는 장치 속도가 아니라 "퍼저가 1초에 명령을 몇 개 보내느냐"이다.

지금 퍼저는 명령마다 다음 순서로 **한 줄로** 진행한다.

```
① 샘플링 시작(스레드 생성)
② nvme 명령 실행 ── 장치는 예: 1ms 만에 끝냄
③ 샘플링 정지 요청 → 샘플링 스레드가 끝날 때까지 기다림(join)   ← 여기서 시간이 샌다
④ 커버리지 회계
⑤ 다음 명령
```

③에서 샘플링 스레드는 하던 일을 **바로 그만두지 못한다.**

- J-Link USB 호출 하나는 중간에 끊을 수 없다.
- 일부 단계는 정확성을 위해 **반드시 끝까지** 해야 한다. 예를 들어 SBA 주소를 바꾼 뒤의 검증이나 오버레이 bank 확인이다.
  중간에 멈추면 SBA 가 반쯤 바뀐 상태로 남고, 다음 창에서 **다른 코어의 PC 를 이 코어 값으로 읽는** 오염이 생긴다.

그래서 장치는 1ms 만에 끝냈어도, 퍼저는 그 뒤 수십 번의 USB 왕복이 끝날 때까지 다음 명령을 보내지 못한다.
`--no-jlink` 에는 ①③이 없으니 같은 장치·같은 명령에서도 exec/s 차이가 크게 난다.

### 1.3 PM9M1 은 왜 괜찮은가

| | PM9M1 | BM9K1 |
|---|---|---|
| PC 1개 읽기 | DAP 레지스터 1회 읽기 | SBA 로 PCSR 1회 읽기(같음) |
| 코어 바꾸기 | 없음 | SBA 주소 바꾸기 — **약 16왕복** |
| 오버레이 확인 | 없음 | 프로브 주소로 옮겨 읽고 되돌아오기 — **약 17 + 16왕복** |
| 멈출 때 남는 일 | 읽기 1회 | 끝 bank 확인 **17왕복**(중단 불가) |

PM9M1 은 멈추는 데 거의 시간이 안 든다. BM9K1 은 "주소 옮기기"가 작업 단위라서 멈출 때마다 비싸다.

### 1.4 오버레이 확인도 코어 이동과 같은 비용이다

SBA 입장에서 "코어 이동"은 **sbaddress0 를 다른 코어의 PCSR 주소로 바꾸는 일**이다.
오버레이 bank 확인도 똑같이 주소를 바꾼다(PCSR → 오버레이 프로브 주소 → 다시 PCSR).
하드웨어는 둘을 구분하지 않고 비용도 같다.

오버레이 코어(현재 자산 기준 H) burst 1회는 이렇게 돈다.

```
[H 로 이동]      PCSR(H)  → 프로브    시작 bank 읽기   17왕복
                 프로브    → PCSR(H)   pin 복귀         16왕복
                 PC 읽기 × N           burst
                 PCSR(H)  → 프로브    끝 bank 확인     17왕복  ← 명령이 끝나도 중단 불가
[다음 코어]      프로브    → PCSR(X)                    16왕복
```

H 코어 가중치가 8/14 라서, 한 창의 주소 이동은 **코어 4개 사이 이동보다 H 의 오버레이 확인이 2~3배 많다.**
"코어 4개를 오가서 느리다"는 직관은 절반만 맞고, 실제로는 오버레이 확인이 더 크다.

### 1.5 왜 부분 수정이 아니라 구조를 바꾸나

다음 부분 수정도 검토했다.

- 끝 bank 확인을 줄이거나 다음 창 시작 확인으로 대체하기
- 창이 끝날 때 PCSR 로 되돌려 두기
- 1000명령마다 한 코어만 보는 식으로 코어 이동 줄이기

모두 **"명령마다 샘플링을 세우고 기다린다"는 구조를 그대로 둔 채** 대기를 조금 줄이는 것이다.
특히 1000명령 단위 코어 고정은 시간 구간과 명령 종류가 엮여 커버리지가 편향되고(F 코어 구간에 실행된 명령의 H 경로는
영영 안 보임), 오버레이 확인 비용도 그대로 남는다.

원하는 것은 **코어를 멈추지 않는 PC 샘플링이 명령 실행과 따로 도는 것**이다. 그러려면 샘플링을 명령 루프에서 떼어 내야 한다.
위 부분 수정은 모두 "준비 비용이 명령 시간 안에 들어가 짧은 명령의 샘플이 사라지는" 문제(§1.1-2)를 풀지 못한다.

### 1.6 과거에 같은 방식을 제거한 기록이 있다 (v8.7)

v8.6 에 상시(always-on) PCSR 폴링이 있었고, v8.7 에서 **완전히 제거**했다(`backup/pc_sampling_fuzzer_v8.7.md`).
긴 캠페인 중 호스트 Ubuntu freeze 가 always-on 도입 뒤에 나타났고, "비침습은 SSD 기준이지 호스트 기준이 아니다"라고 판단했다.

- 그 뒤 조사에서 호스트 즉시 재부팅의 원인은 주기 차트 `os.fork()`(검증됨), segfault 계열은 진단용 커널 debug 옵션으로 밝혀졌다.
  v8.7 의 판단은 상관관계였고 always-on 이 원인이라고 증명된 적은 없다.
- 그때는 OpenOCD telnet 경로였고 지금은 J-Link DLL 직접 호출이라 경로도 다르다.
- 그래도 **상시 USB 디버그 트래픽이 호스트에 안전하다는 것도 증명되지 않았다.** 그래서 opt-in 으로 시작하고,
  즉시 되돌릴 수 있게 하며, 첫 실기에서 호스트 상태(dmesg, 메모리, 커널 경고)를 함께 본다.
- 참고로 지금 방식도 명령이 연달아 나가는 동안에는 샘플링 시간 비율이 이미 높다. 상시 모드에서 새로 늘어나는 것은 명령 사이와
  긴 대기 구간의 트래픽이다.

## 2. 목표 구조

### 2.1 지금 (명령마다 동기식 창)

```
메인:   [시작]─명령─[정지·대기]─회계─[시작]─명령─[정지·대기]─회계─ …
워커:    ├─준비─burst─끝확인┤        ├─준비─burst─끝확인┤
```

### 2.2 v11.3 (상시 백그라운드)

```
워커:   ─burst─확인─burst─확인─burst─확인─ … (캠페인 내내, 샘플마다 포착 구간 기록)
                      └ "이 시각 이전 샘플은 모두 확정" 경계(확정 시각)를 계속 앞으로 민다
메인:   ─명령1─명령2─명령3─명령4─ …  (명령 시작·끝 시각만 남기고 기다리지 않음)
          │     │     │
          └─────┴─────┴→ 대기열(pending): 확정 시각이 명령 끝을 넘으면 실행 순서대로 커버리지 회계
```

- 메인 루프는 샘플링을 기다리지 않는다. v11.2.1 실측상 기다리던 시간은 이미 1ms 미만이라 exec/s 이득은 작다(§1.1). 주 목적은 짧은 명령의 샘플 확보다.
- 주소 이동·오버레이 확인·짧은 경로 실패 시 전체 경로 같은 비용은 **샘플 밀도만 줄이고 명령 전송은 막지 않는다.**
- 창마다 처음부터 준비하지 않으므로, 짧은 명령에서 준비하다 끝나 샘플이 0개가 되던 일도 줄어든다.

### 2.3 커버리지를 세 갈래로 관리

| 구분 | 무엇 | 전체 커버리지 | 새 커버리지 판정 |
|---|---|---|---|
| 명령 귀속 | 포착 구간이 명령 실행 구간 안에 확실히 드는 샘플 | 반영 | **판정 대상** |
| 백그라운드 | 명령 사이·명령 뒤 후처리 구간, 경계가 애매한 샘플 | 반영 | 판정에 쓰지 않음 |
| idle 기준선 | 시작 시 diagnose 로 모은 무명령 PC(기존) | 반영 | 판정 기준 집합에 포함 |

**판정 기준 집합 = 명령 관측 집합 ∪ 시작 시 idle 기준선**(방식 B, §3.1). 백그라운드 집합은 여기에 넣지 않는다.

- 백그라운드 샘플은 "특정 명령의 성과"로 치지 않지만 버리지도 않는다. 펌웨어가 실제로 실행한 코드이므로 전체 커버리지에 기록한다.
- 보고서에는 `명령 BB / 백그라운드 전용 BB / 전체 BB` 로 나눠서 보여 준다.
- **구현 주의**: 지금 `CoverageModel.account()` 는 `covered_bbs` 하나를 갱신하고 그것과 비교한다.
  백그라운드가 같은 집합을 갱신하면 방식 B 가 실제로는 적용되지 않는다. 판정용 집합과 전체 집합을 분리해야 한다.

**판정 기준 집합에 들어갈 자격** — 명령 귀속 샘플이라도 아래를 **모두** 만족하는 명령의 것만 판정 기준 집합을 갱신한다.

1. 명령이 대기열에서 **확정**으로 끝났다(§3.3 의 "관측 미확정"으로 끝나지 않았다).
2. 명령 구간이 무효 구간(§3.4)과 겹치지 않는다.
3. 전송이 확인됐다. rc 만으로 판단하지 않는다. 커널이 SQE 를 만들기 전에 errno 로 거절해도 양수 rc(예: rc=1)가 나온다.
   **실제 제출 판정(`_last_cmd_submitted`)이 참이고 NVMe 완료 상태(`_last_nvme_status`)가 있으며 timeout 이 아닌** 명령만 해당한다.
4. 그 명령의 관측에 버퍼 넘침·관측 실패가 없다(§3.9).

조건을 못 채운 명령이 본 BB 는 **전체 커버리지에만** 넣는다. 판정 기준 집합을 먼저 갱신하고 보상만 취소하면,
그 뒤 정상 명령이 같은 BB 를 밟아도 new = 0 이 되어 발견 기회를 잃는다. 백그라운드가 공을 가로채지 않게 하려던 방식 B 의 목적과 같은 이유다.

### 2.4 켜고 끄기

- 설정: BM9K1 `riscv.sample_plan.background.enabled: true`(객체 대신 `true` 만 써도 된다). 기본값은 실기 확인 전까지 false.
  상한·제한 시간도 같은 객체에 둔다(§10.3).
- false 면 v11.2.1 창 방식 그대로 동작한다. 코드 경로를 남겨 두고 같은 파일에서 바로 되돌릴 수 있게 한다.
- 실행 기록(run_record)의 `conditions` 에 샘플링 방식을 남긴다(§3.14).

## 3. 대가 — 바뀌는 것과 위험

### 3.1 새 커버리지 판정 기준 — 방식 B 로 결정

"이 명령이 새 코드를 밟았나"를 **무엇과 비교할지**에 따라 결과가 갈린다.

**A. 전체 커버리지와 비교 (채택 안 함)**
- 백그라운드가 먼저 본 BB 는 나중에 명령이 밟아도 new = 0 이다.
- 명령의 공을 백그라운드가 **가로챈다.** 예를 들어 Write 뒤의 캐시 플러시 코드가 명령이 끝난 직후(백그라운드 구간) 먼저 잡히면,
  나중에 그 코드를 명령 안에서 밟는 Write 가 corpus 에 들어갈 기회를 잃는다.

**B. 명령 관측 집합 ∪ idle 기준선과 비교 (채택)**
- 공정하다. 대신 백그라운드에서만 보이던 BB 를 어떤 명령이 처음 밟으면 1회 interesting 이 된다.
- idle 루프처럼 늘 도는 코드는 idle 기준선이 막아 준다.

### 3.2 즉시 처리와 지연 회계를 나눈다

지금 회계 함수(`_account_command`, v11.2 10130행)는 실행 횟수, SC, timeout 처리, corpus 갱신을 한 번에 한다.
이 함수를 통째로 늦추면 **timeout 중단이나 학습 시퀀스의 setup 실패 처리까지 늦어진다.** 그러면 이미 깨진 장치에 다음 명령을 보낼 수 있다.

그래서 명령 결과를 두 부분으로 나눈다.

| 명령 완료 즉시 (기다리지 않음) | 샘플이 확정된 뒤 (지연 회계) |
|---|---|
| 실행 횟수·명령별 실행 수·rc 집계 | 이 명령의 커버리지(새 BB 수, interesting) |
| NVMe 상태(SC) 집계, 신규 SC, SC-depth 전진 기록 | corpus 추가, det 큐 진입 |
| timeout·장치 소실 → crash 처리(§3.5) | CSFuzz 보상, MOpt 발견 수(`mopt_finds`) |
| 추적 PS 갱신, FWCommit 처리, Write Protect, NS 재부착 | 시드 staleness(`last_gain_exec`) |
| 시퀀스 멤버 기록, 학습 시퀀스 진행·setup 성공/실패 판정 | 학습 관측의 커버리지 부분, ledger, 대조 풀의 new_pcs |
| MOpt 사용 수(`mopt_uses`) | 코어별 수확·적응형 가중치(§3.9) |

- **SC-depth 전진만으로 interesting 이 되는 경우**(커버리지 0): 판정에 필요한 값은 즉시 기록해 두고, corpus 추가는 같은 명령의
  지연 회계 때 한 번에 한다. corpus 추가 지점을 하나로 유지하려는 것이다.
- 학습 모듈(`llm_learning.py`)의 관측도 상태 부분(즉시)과 커버리지 부분(지연)으로 나눠야 한다. 구현 전에 그 모듈의 호출 계약을 확인한다.

**주기 작업은 실행 수가 아니라 "경계를 넘은 횟수"로 한 번씩 돌린다.**
지금 `_account_command` 안에는 `executions % 100`(Stats·window 초기화), `% 10000`, VMON, halt health,
state capture(`% 100`) 같은 조건이 있다. 실행 수(즉시 증가)와 지연 회계 시점이 갈라지면 이 조건이 깨진다.

- 실행 수가 100 이 된 뒤 대기 명령 20개를 회계하면 `executions % 100 == 0` 이 20번 참이 되어 같은 작업이 20번 돈다.
- 98 에서 103 으로 한 번에 넘어간 뒤 회계하면 100 경계를 놓친다.

규칙
- 주기 작업마다 "다음 경계"(`next_at`)를 두고, 카운터가 그 값을 넘으면 **한 번** 실행하고 `next_at` 을 다음 배수로 옮긴다.
  여러 경계를 한꺼번에 넘었으면 한 번만 실행한다(따라잡기 반복 없음).
- 어떤 카운터로 셀지 작업마다 정한다. nvme 명령을 실제로 보내는 state capture, 로그 fsync, VMON·halt health 는
  **실행 수 기준·즉시 쪽**에서 돈다. 커버리지 수치가 들어가는 `[Stats]`·cull·그래프는 **회계 완료 수 기준·지연 쪽**에서 돈다.
- state capture 가 interesting 이면 `_cmd_history` 로 상태 시퀀스를 만든다. 이 이력은 **캡처 순간의** 것이어야 하므로
  캡처를 즉시 쪽에 두고 이력도 그때 복사한다. 지연 쪽으로 옮기면 그 사이 실행된 명령이 시퀀스에 섞인다.

### 3.3 대기열(pending)과 확정 경계

**회계는 명령 1개가 아니라 여러 개 밀릴 수 있다.** burst 하나(256 읽기 + bank 확인)가 끝나는 동안 짧은 명령 수십 개가 실행될 수 있고,
준비·bank 읽기가 늦어지면 더 밀린다. 그래서 다음 규칙을 둔다.

1. **명령 ID**: 전송할 때마다 단조 증가 ID 를 붙인다.
2. **스냅샷 두 개**
   - 전송 전 입력: seed, source, `_current_mutations`, `_credit_seed`, 시퀀스·학습 컨텍스트, det 여부, 시퀀스 멤버 여부
   - 완료 후 결과: rc, `_last_nvme_status`, `_last_wire`, `_last_cmd_submitted`, 신규 SC·depth 전진 여부, 명령 시작·끝 시각, 세션 세대(§3.4)
   - 지금 회계 함수는 회계 순간의 `self.*` 를 읽는다. 스냅샷 없이 늦추면 **오류 없이 조용히** MOpt·LLM 보상이 다른 명령에 붙는다.
   - **스냅샷은 바뀌지 않아야 한다.** 다음 명령이 같은 객체를 고치면 스냅샷도 바뀐다.
     - `bytes` payload 는 불변이라 참조로 공유해도 된다.
     - 변이 목록·mutation 이름 등 작은 가변 값은 tuple 로 복사한다.
     - seed 객체·시퀀스·학습 컨텍스트처럼 계속 바뀌는 객체는 참조하지 않는다. 보상 대상 부모 seed·시퀀스·학습 실험은 **ID** 로 남기고,
       회계 때 ID 로 찾는다. 그 사이 cull 등으로 없어졌으면 그 보상만 건너뛴다.
3. **확정 시각(= 처리 완료 경계)**: 워커가 "이 시각 이전에 포착된 샘플은 모두 처리가 끝났다(채택 또는 폐기)"인 시각을 계속 공개한다.
   raw 읽기 성공만으로는 앞으로 밀지 않는다. burst 의 채택·폐기가 결정됐을 때 그 burst 끝까지 민다(§3.4).
   정상 bank 스왑으로 burst 를 **폐기한 경우에도** 처리는 끝났으므로 전진한다. 폐기 구간은 무효 구간으로 같이 공개한다.
   대기 명령 종료는 이 경계로 한다. 장애 영향 범위는 이것과 다른 "정상 검증 경계"로 정한다(§3.4).
   - 샘플 묶음·무효 구간·확정 시각은 **하나의 묶음으로 한 번에** 공개한다. 메인이 "확정 시각은 새 값인데 그 앞의 무효 구간은 아직 안 보이는" 중간 상태를 읽으면 안 된다.
     워커가 묶음을 큐에 넣고, 메인은 큐에서 묶음 단위로 꺼낸다.
4. **실행 순서대로 회계**: 대기열 맨 앞 명령의 끝 시각이 확정 시각 이전이면 회계하고 꺼낸다. 순서를 건너뛰지 않는다.
5. **상한과 초과 정책**
   - 대기 명령 수(예: 256), 최대 지연 시간(예: 2초), 스냅샷 payload 메모리(seed data 는 최대 128KB 라 복사하지 않고 참조로 보관)에 상한을 둔다.
   - **최대 지연 시간은 명령 완료 시각부터 잰다.** 전송 시작부터 재면 정상적인 긴 Format·Write 가 샘플러 지연으로 오인된다.
     명령이 실행 중인 동안은 지연으로 치지 않고, 완료 뒤에도 확정 시각이 그 명령 끝을 넘지 못할 때만 센다.
   - 상한에 닿으면 확정 시각이 앞으로 갈 때까지 메인이 **짧게(상한 있게)** 기다린다.
   - 그래도 확정 시각이 멈춰 있으면 워커 이상으로 보고 장애 경로로 간다(§3.4, §3.6). 해당 명령들은 "관측 미확정"으로 회계한다.
     실행 수는 세고, 커버리지 보상은 주지 않는다(기존 `coverage_unobserved` 와 같은 의미).
6. **메인 스레드에서만 corpus 를 바꾼다**: 지연 회계는 메인 루프의 정해진 지점(반복 시작 등)에서만 실행한다. 워커는 샘플만 만든다.
7. **명령 하나는 한 번만 끝난다**: 명령 상태는 `pending → 확정` 또는 `pending → 관측 미확정` 중 하나로 **딱 한 번** 바뀐다.
   - 끝난 명령 ID 는 대기열과 스냅샷 참조에서 바로 지운다(메모리 잔류 방지).
   - 상한 초과나 crash flush 제한 시간으로 "관측 미확정"으로 끝낸 뒤 그 구간의 검증이 늦게 끝나도 **보상에 다시 쓰지 않는다**(중복 보상 방지).
     늦게 검증된 샘플은 전체 커버리지에만 백그라운드로 넣는다. 검증 실패로 끝난 샘플은 어디에도 넣지 않는다.
   - 메인은 "마지막으로 끝낸 명령 ID"를 두고, 그 이하 ID 를 가리키는 결과는 귀속 단계에서 버린다.

### 3.4 장애로 관측이 무효가 되는 범위 — 세션 세대와 불확실 구간

"오류 시각이 명령 구간 안에 있으면 무효"라는 규칙만으로는 부족하다.
오류가 명령 사이에 검출되거나, burst 전체 실패·bank 확인 실패로 **나중에** 드러나면 그 앞 명령들도 영향을 받는다.

- **세션 세대 번호**: 연결·재연결·복구·일시정지 후 재개마다 1씩 올린다. 모든 샘플과 명령 스냅샷에 세대를 기록한다.

**"마지막 정상 읽기"와 "검증된 관측"은 다르다.**
PC 읽기가 모두 성공해도 오버레이 코어는 burst 끝 bank 확인이 통과해야 그 burst 샘플을 쓸 수 있다.
끝 확인이 실패하면 burst **앞부분까지** 검증되지 않은 것이다. "마지막 PC 읽기 성공 시각 이후"만 무효로 잡으면
그 burst 앞쪽에 걸친 명령들이 빠진다.

**경계 두 개를 따로 둔다.**

| 경계 | 의미 | 쓰는 곳 |
|---|---|---|
| **처리 완료 경계**(= 확정 시각, §3.3-3) | 이 시각 이전 샘플은 채택이든 폐기든 결정이 끝났다 | 대기 명령 종료, 대기열 지연 판정 |
| **정상 검증 경계** | 이 시각까지는 정상 관측이 확인됐다 | 장애가 났을 때 무효 범위의 시작점 |

- burst 가 채택되면 두 경계가 모두 그 burst 끝(마지막 샘플 포착 구간 끝)으로 간다.
  - 오버레이 코어: 끝 bank 확인이 시작 bank 와 같을 때 채택이다.
  - 오버레이가 없는 코어: burst 가 transport 실패 없이 끝나면 채택이다.
- **정상 bank 스왑으로 폐기**하면(두 bank 읽기는 성공, 값만 다름) 처리 완료 경계는 burst 끝으로 가고, burst 구간은 무효로 공개한다.
  이것은 장애가 아니다. 정상 검증 경계도 전진시킨다. 장치와 연결은 정상으로 확인됐고, 그 burst 의 샘플만 bank 를 확정하지 못한 것이다.
  그래서 스왑이 연달아 나도 대기 명령은 계속 끝나고, 워커 정체(§3.3-5)나 transport 장애로 보지 않는다.
- **장애**(읽기 실패, 주소 이동 실패, 세대 변경, 응답 없음)는 정상 검증 경계를 멈춘다. 처리 완료 경계는 무효 범위를 공개한 뒤에 그 범위 끝으로 간다.
  응답 없음이면 처리 완료 경계도 멈추고, §3.3-5 의 상한과 §3.5 로 간다.

**오류 종류별 무효 범위**

| 오류 | 장애인가 | 무효 범위 |
|---|---|---|
| bank 불일치(정상 스왑, 두 읽기 성공) | 아니다 | 그 burst **전체**의 포착 구간(첫 샘플 시작 ~ 마지막 샘플 끝). 샘플은 버린다 |
| bank 읽기 실패 | 맞다 | 직전 정상 검증 경계 ~ 검출 시각(그 burst 전체를 포함) |
| burst 중 PC 읽기 transport 실패 | 맞다 | 직전 정상 검증 경계 ~ 검출 시각 |
| 주소 이동(pin·retarget) 실패 | 맞다 | 직전 정상 검증 경계 ~ 검출 시각 |
| 재연결·복구·일시정지 후 재개(세대 변경) | 맞다 | 직전 정상 검증 경계 ~ 새 세대의 첫 정상 검증 경계. 세대 경계에 걸친 명령 전부 |
| 워커 응답 없음 | 맞다 | 직전 정상 검증 경계 이후 전부 |

- 무효 범위와 겹치는 대기 명령은 학습 근거와 커버리지 보상에서 제외한다(`_learning_window_valid=False` 와 같은 효과). §2.3 자격에서도 빠진다.
- 무효 범위 밖에서 이미 확정된 샘플은 그대로 쓴다.
- bank 불일치는 지금도 "그 burst 버림"(`ovl-drop`)이다. 바뀌는 점은 그 burst 에 걸친 명령을 "샘플 0건"이 아니라 **관측 실패**로 표시하는 것이다.
  관측 실패는 보상에서 빠질 뿐 장애 통계(`sampling 장애`, 재연결 판단)에는 들어가지 않는다.

### 3.5 워커 일시정지와 실패 정책 — 구현 전에 정한다

burst 도중 같은 J-Link 핸들로 다른 접근이 **한 번만** 끼어도 엉뚱한 레지스터를 읽는다(핸들 독점 계약).
지금은 명령 사이에 워커가 멈춰 있어 자연히 지켜졌지만, 상시 모드에서는 세션을 쓰는 모든 경로가
**워커 일시정지 → 작업 → 재개**를 명시적으로 해야 한다.

해당 경로: PM 분리·재연결, FWCommit 재연결, POR 복구, 크래시 처리(`_read_bm9k1_monitor_pc`, J-Link 덤프),
예외 주입 리셋, 가벼운 재연결(reattach), diagnose, 종료.

**일시정지 계약**

1. 호출부가 일시정지를 요청한다.
2. 워커는 진행 중인 DLL 호출 하나를 마치고, 일관된 지점(진행 중 SBA 단계의 검증까지)에서 멈춘 뒤
   **"DAP 접근 없음" 확인 신호**를 보낸다.
3. 호출부는 이 신호를 **받은 뒤에만** close·재연결·덤프·새 워커 생성을 한다.

**확인 신호가 제한 시간 안에 안 오면**

- close·재연결·새 워커 생성을 **하지 않는다.** 파이썬 스레드는 강제로 끝낼 수 없고, DLL 호출 안에 있는 핸들을 닫으면 결과를 알 수 없다.
- 샘플러를 "응답 없음"으로 표시하고 **제한 시간 안에 캠페인을 중단**한다(증거 수집 후 종료).
- 종료 정리(`finally`·atexit·리포트 생성)에서도 "응답 없음" 표시를 보고 막힌 세션의 `close()` 를 **다시 부르지 않는다.** 정리 경로가 lock 을 기다리며 멈추면 중단 자체가 끝나지 않는다.
- 지금 코드의 위험 두 가지를 같이 고친다.
  - `_stop_worker()` 는 워커가 살아 있어도 `sample_thread = None` 으로 참조를 비운다(v11.2 4039행). 그 뒤 새 워커가 생기면 두 워커가 같은 핸들을 쓴다.
  - 세션 `close()` 는 세션 lock 을 기다리는데, 멈춘 워커가 lock 을 쥐고 있으면 메인도 같이 멈춘다.

**재개 누락 감시**: 지금 이 경로들은 `_stop_worker()` 뒤 "다음 명령이 샘플링을 다시 시작한다"에 기대고 있다.
상시 모드에서 재개를 빠뜨리면 **커버리지 0 으로 조용히 돈다.** "명령 구간에 샘플 0 + 워커 정지 상태"가 연속되면 경고한다.

**crash 시**: 대기 회계 확정(flush)을 무한정 기다리지 않는다. 제한 시간 안에 확정된 것만 회계하고,
나머지는 **미확정 목록**(명령 ID·시드·rc)을 crash 폴더에 남긴 채 증거 수집으로 넘어간다.
워커가 응답 없음이면 J-Link 가 필요한 덤프는 건너뛰고, PCIe 경로 덤프(UFAS)와 로그·dmesg 는 수집한다.

### 3.6 장애 감지와 복구

v11.2.1 원칙을 유지한다. 워커는 오류를 표시만 하고, 복구(APST·keepalive 끄기 → 재초기화/재연결)는 메인 루프가 한다.

- 워커가 오류를 세우면 메인은 다음 명령 경계에서 일시정지(§3.5) → 복구 → 세대 증가 → 재개를 한다.
- 무효 범위는 §3.4 규칙으로 정한다.
- 명령마다 join 하던 구조가 없어지므로 "join timeout 뒤 살아 있는 옛 워커를 재사용해 그 명령이 샘플링 없이 도는" 코드상 결함은
  (2026-10-15 로그에서 실제로 일어나지는 않았다, §8) 이 구조에서는 사라진다. 대신 §3.5 의 일시정지 timeout 이 그 역할을 맡는다.

### 3.7 기다려서 바로 확정해야 하는 지점 (flush)

대기열 회계를 제한 시간 안에서 기다려 확정하는 지점이다. 진행 중 burst 의 확인을 기다리므로 **그 순간만** 대기가 생긴다.
드물게 일어나서 전체 속도에는 영향이 작다. 제한 시간을 넘기면 §3.3 의 "관측 미확정"으로 처리한다.

| 지점 | 이유 |
|---|---|
| 캘리브레이션(`_calibrate_seed`) | 같은 시드를 여러 번 돌려 결과를 바로 비교한다 |
| state replay(`_replay_state`) | 재생한 명령의 결과로 성공 여부를 판단한다 |
| 시퀀스 종료(`_finalize_seq_sink`) | 시퀀스 전체가 interesting 인지 마지막에 판정한다 |
| PM 슬롯 진입 전 | BM9K1 은 PM 동안 세션을 닫는다 |
| timeout·crash 처리 | §3.5 — 제한 시간 뒤 미확정 목록을 남기고 진행 |
| 퍼저 종료 | 마지막 명령 회계 |

### 3.8 샘플의 포착 시각과 경계 처리

명령 구간으로 나누려면 각 샘플이 "언제 포착된 PC 인지"를 알아야 한다. **읽기가 끝난 시각과 PC 가 포착된 시각은 다르다.**

- 지금 SBA 는 FIFO 모드(`sbreadondata`)라서 **SBDATA0 를 읽으면 그 읽기가 다음 bus read 를 시작한다.**
  즉 i 번째 DRW 읽기가 돌려주는 값은 **i-1 번째 읽기가 시작시킨 bus read** 가 포착한 PC 다.
- burst 의 첫 값은 **SBA 파이프라인에 마지막으로 read 를 시작시킨 접근**의 결과다. 코어를 옮겼으면 준비 단계의 주소 쓰기지만,
  같은 코어에 이미 핀돼 있으면 `_pin()` 이 바로 반환하므로(`riscv_cov.py` 1198행) **이전 burst 의 마지막 DRW 읽기**가 시작시킨 값이다.
  준비가 길었거나, 같은 코어 burst 사이에 다른 일이 있었거나, 일시정지 직후라면 한참 전에 포착된 값일 수 있다.
- 따라서 반환 직후 시각만 찍으면 **명령 시작 전에 포착된 PC 가 그 명령으로 붙을 수 있다.**

규칙

**트리거 호출이 반환됐다고 bus read 가 끝났다는 보장은 없다.** DRW 읽기 호출은 SBDATA0 값을 받아 오면 반환하고,
그 읽기가 시작시킨 다음 bus read 는 장치 안에서 그 뒤에 진행될 수 있다. 짧은 경로(`sba_retarget`)가 주소 쓰기 뒤
busy 완료를 **따로** 폴링하는 것도 같은 이유다. 핫루프(`sba_read_pinned`)는 DRW 읽기 1회뿐이라 완료를 확인하지 않는다.
그래서 포착 시각의 상한을 "트리거 호출 반환 시각"으로 잡으면, 그 뒤 명령 경계를 넘어 포착된 PC 가 앞 명령에 붙을 수 있다.

1. 읽기마다 호출 직전·직후 시각을 남긴다. 샘플 i 의 **포착 구간 = [그 값을 시작시킨 접근의 호출 직전, 그 값을 회수한 호출(i 번째 읽기)의 직후]** 로 잡는다.
   하드웨어 완료 시점을 입증하지 못하므로 시작과 회수 사이 전체를 포착 가능 구간으로 본다(보수적).
   - 평소에는 [i-1 번째 읽기 직전, i 번째 읽기 직후], 즉 USB 왕복 약 2회 폭이다.
   - burst 첫 샘플의 시작은 아래 2 의 "마지막 트리거" 직전이다.
2. **트리거 이력은 burst 가 아니라 SBA 파이프라인 상태를 따라 관리한다.** 샘플러는 "지금 진행 중인 bus read 를 시작시킨 접근의 호출 직전 시각"(마지막 트리거)을 하나 들고 있고,
   PCSR 값을 돌려받을 때마다 그 값을 포착 구간 시작으로 쓴다.
   - **주소를 실제로 다시 썼을 때**(pin 전체 경로, retarget, `read_word` 뒤 PCSR 로 복귀, 재연결 뒤 pin): 마지막 트리거를 그 주소 쓰기 직전으로 바꾼다.
     `read_word` 는 프로브 주소로 read 를 하나 더 시작해 두므로, 그 뒤 PCSR 로 돌아오는 주소 쓰기 전까지의 값은 PC 샘플로 쓰지 않는다.
   - **같은 핀을 유지했을 때**(같은 코어 연속 burst — `_pin()` 즉시 반환): 이전 burst 의 마지막 트리거를 **그대로 이어받는다.**
     burst 시작 시각을 새 트리거로 쓰지 않는다. 이어받은 구간은 burst 사이 시간만큼 넓어지므로 그 사이에 명령 경계가 있었으면 저절로 애매 처리된다.
   - 일시정지 뒤 재개도 같다. 주소를 다시 썼으면 새로 시작하고, 핀이 그대로면 일시정지 전 트리거를 이어받는다(구간이 일시정지 시간만큼 넓어진다).
   - 읽기 실패(`None`)가 끼면 그 호출이 새 bus read 를 시작했는지 모른다. 마지막 트리거를 **마지막 성공 읽기 호출 직전**에 그대로 두어,
     다음 성공 샘플의 시작이 그만큼 넓어지게 한다.
   - **이력을 알 수 없으면**(상태가 `_DIRTY`·`None`, 중단된 주소 이동 뒤, 세대가 바뀌었는데 주소 쓰기를 확인하지 못함) 다음 첫 샘플은 명령 보상에서 제외하고
     백그라운드로만 쓴다. 그 다음 샘플부터는 그 첫 읽기가 트리거다.
3. 포착 구간이 명령 실행 구간 **안에 완전히 들면** 명령 귀속, **밖에 완전히 있으면** 백그라운드다.
4. **걸치면(애매하면)** 명령 보상에서 제외하고 백그라운드로 보낸다. 전체 커버리지에는 들어간다.
5. burst 의 첫 샘플과 실패 직후 샘플은 구간이 넓어 대부분 애매 처리된다. 정확성을 위해 감수한다.
   구간 폭이 2왕복이 되므로 아주 짧은 명령(2왕복보다 짧은 실행)은 명령 귀속 샘플이 0개일 수 있다. 실기에서 애매 처리 비율을 잰다(§7).

- 핫루프에 시각 읽기 2회(`time.monotonic()`, 수백 ns)를 더한다. 핫루프 금지 규칙(`sjtag_unlock.py` 주석)은
  DAP 접근·지연·재시도에 대한 것이라 해당하지 않지만, 실측으로 정한 규칙의 영역이므로 실기에서 읽기 실패율 변화를 확인한다.
- "경계 오차는 USB 왕복 1회"라고 보장하지 않는다. 위 규칙으로 애매한 샘플을 빼는 것으로 대신한다.

### 3.9 샘플 수 집계와 적응형 가중치

고유 키만 모으면 정보가 사라진다. 고유 키 집계와 함께 다음을 유지한다.

- 코어별·구간별 **유효 / 무효(halt·WFI) / 읽기 실패** 샘플 수
- 코어별 관측 수(적응형 가중치 입력)
- 버퍼 넘침 여부와 넘친 샘플 수

적응형 가중치(`_adaptive_weights_step`)는 지금 **샘플 수**를 쓴다. 중복 제거된 키 수로 바꾸면 의미가 달라지므로 샘플 수를 그대로 넣는다.
입력은 **명령 귀속 샘플만**이다. 백그라운드까지 넣으면 명령이 없을 때 바쁜 코어 쪽으로 가중치가 쏠린다.

**"관측 0건"과 "버퍼 넘침"과 "관측 실패"를 구분한다.** 셋 다 새 BB 가 0 으로 보이지만 의미가 다르다.
넘침·실패는 보상에서 제외하고 통계에 따로 센다.

### 3.10 메모리 상한

지금은 창당 500 샘플 상한이 있다. 상시 모드에서는 긴 명령(Format 180s, 긴 Write)이나 긴 대기(PM sleep)
하나에 수십만 샘플이 들어올 수 있다.

- 워커는 샘플을 전부 쌓지 않고 **구간별 고유 키(코어·bank·주소) + §3.9 의 수치**만 모은다.
- 메인이 오래 가져가지 않을 때(LLM 처리, 보고서 생성 등)를 대비해 버퍼 상한을 두고 넘침을 센다.
- 상한은 대기열(pending)만이 아니라 **워커 결과 큐**(공개 묶음 수)와 **burst 임시 버퍼**(채택·폐기 결정 전 샘플)에도 둔다.
  결과 큐가 차면 워커는 묶음을 합쳐 고유 키·수치만 남기고 넘침을 센다. 구체 값은 구현 단계에서 정한다.
- `max_samples_per_run`, 포화 기록(`_unique_at_intervals`)은 BM9K1 상시 모드에서 의미가 없어진다.

### 3.11 오버레이 판별 — drop 증가와 잘못된 bank 귀속

오버레이 bank 는 burst **앞뒤**에서 읽어 같으면 그 burst 샘플을 그 bank 로 인정하고, 다르면 burst 전체를 버린다.

- **drop 증가**: 지금은 명령이 끝나면 burst 가 짧게 끊겨 앞뒤 확인 사이 간격이 짧았다. 상시 모드에서는 burst 가 끝까지(256 ± 20%)
  읽으므로 그 사이 스왑이 일어날 확률이 오르고, 버리는 샘플(`ovl-drop`)이 늘 수 있다.
- **잘못된 귀속**: 앞뒤 bank 가 같아도 중간에 A→B→A 로 바뀌었다면 B 의 PC 를 A 로 인정한다. 기존 방식에도 있는 한계지만
  burst 가 길어지면 확률이 오른다.
- **적용 범위**: 현재 자산(`products/BM9K1/overlay_coreH.json`)은 H 뿐이지만 코드는 프로브가 있는 모든 코어에 적용된다.
  F 등 다른 코어에 오버레이 맵이 생기면 같은 규칙을 따른다.

대응
- 오버레이 코어의 burst 길이를 따로 짧게 둔다(초기값 64). **이것은 완화책이지 정확성 보장이 아니다.**
- 실기에서 스왑 빈도를 잰다. 단, **연속 bank 확인 사이에서 본 변화 빈도는 관측된 변화일 뿐이다.** 앞뒤 확인 사이의
  A→B→A 는 보이지 않으므로, 그 값만으로 "burst 안에서 두 번 스왑할 확률이 작다"고 입증할 수 없다(실제 스왑 빈도의 하한일 뿐).
  - 실제 빈도를 보려면 퍼징과 따로, 프로브 주소만 연속으로 읽는 **측정 모드**로 bank 값을 촘촘히 기록해 스왑 간격 분포를 잰다.
    그 간격이 burst 길이보다 충분히 길 때만 burst 길이를 늘린다.
  - 측정 전에는 오귀속 가능성이 남아 있다고 보고 64 를 유지한다.
- 짧은 burst 는 확인 33왕복이 burst 마다 붙어 샘플 밀도를 줄이지만, 그 비용은 이제 명령 전송을 막지 않는다.

### 3.12 명령 뒤 후처리 PC — 꼬리 0ms

v11.2.1 은 명령이 끝나면 즉시 샘플링을 멈춰 후처리 구간(캐시 플러시·로그 기록 등)을 버렸다.
v11.3 에서는 그 구간이 백그라운드로 잡힌다. 전체 BB% 는 오르고, 명령 귀속은 "명령 실행 구간 안"이라는 의미를 유지한다.
명령 뒤 일정 시간을 그 명령에 귀속하는 꼬리 설정은 두지 않는다(0ms).

### 3.13 코어 전환

- 코어 전환은 그대로 된다. 스케줄 루프(가중치 → 셔플 → burst)는 명령과 무관하게 계속 돈다.
- 짧은 명령은 그 순간 돌던 코어 하나만 본다. 지금도 창의 첫 코어가 무작위라 사실상 같고, 여러 명령에 걸쳐 가중치 비율대로 평균이 맞는다.
- burst 하나가 길면 그동안 다른 코어는 관측 공백이다. 짧게 하면 공백은 줄고 전환 비용은 늘지만, 그 비용은 명령 전송을 막지 않는다.
- 실기에서 코어별 명령 귀속 샘플 비율이 가중치와 맞는지 확인한다.

### 3.14 실행 비교 — 비교 도구도 고친다

**`compare_runs.py` 는 버전으로 실행을 나누지 않는다.** 기본 그룹은 `llm` 이고, `version` 은 비교 가능성 검사에서
제외되는 키(`_RUN_LEVEL`)다. 그대로 두면 v11.2 와 v11.3 실행이 같은 그룹에 섞인다.

- 실행 기록 `conditions` 에 `sampling_mode`(window / background), `attribution_policy`(B, 꼬리 0ms, 경계 규칙),
  지표 의미(전체 BB 에 백그라운드 포함 여부)를 남긴다.
- `compare_runs.py` 에서 이 키들을 반드시 일치해야 하는 조건(`_MUST_MATCH` 와 같은 수준)으로 다루거나, 다르면 비교를 막는다.
- 명령 귀속 BB 도 샘플 예산·관측 방식이 달라 **v11.2 와 완전히 같은 측정은 아니다.** 버전 간 비교는 참고용으로만 본다.
- 참고: `docs/V11_2.md` §3 의 "버전이 달라 compare_runs.py 가 한 그룹으로 섞지 않는다"는 설명도 같은 이유로 틀렸다.

### 3.15 명령이 빨라지면 "N명령마다" 하는 일이 잦아진다

exec/s 가 오르면 명령 수 기준 주기 작업의 실제 시간 간격이 짧아진다.

- `[Stats]` 출력과 로그 fsync(100명령마다)
- state monitor capture(100명령마다, nvme 명령을 실제로 보냄)
- **PM 슬롯(100명령마다, BM9K1 은 세션을 닫았다 다시 연다 — 수 초)**

**PM 주기는 처음에는 바꾸지 않는다.** 같은 PM 주기에서 샘플러 변경 효과를 먼저 재야 속도 향상이 어디서 왔는지 가를 수 있다.
그 뒤 PM 재연결 비중을 보고 따로 조정한다.

로그도 초당 양이 exec/s 에 비례해 늘어난다. `_account_command` 의 `ALL raw PCs` debug 문자열은 로그 레벨과 무관하게
매번 만들어지므로 함께 정리한다.

### 3.16 그 밖의 경로

| 경로 | 처리 |
|---|---|
| 명령 timeout(장치 행) | 워커가 계속 PC 를 읽어 행 지점 PC 가 백그라운드로 쌓인다 — 진단에 이득. crash 처리는 §3.5 |
| FWCommit 활성화 | 코어 리셋 직후 잠깐 다른 상태의 PC 가 들어온다. 범위 밖 필터가 걸러 주지만 그 구간은 불확실 구간(§3.4)으로 처리한다 |
| 예외 주입(`ExceptionFuzzerMixin`) | **첫 구현은 지원하지 않는다.** `background: true` 와 예외 주입(`exceptions.enabled` 또는 `--exception`)이 함께 켜지면 **기동 단계에서 거부**하고 종료한다. 검증 없이 지원 조합으로 남겨 두지 않는다. 나중에 지원할 때 리셋 이벤트 중 워커 일시정지와 `recovery_observation` 의 시각 구간 재정의를 한다 |
| FWDownload 청크 묶음 | 실행 구간 = 첫 청크 시작 ~ 마지막 청크 끝 |
| 다른 제품 | 기존 창 방식 유지 |

  창 방식(`background: false`)에서는 그대로 통과해야 한다.

### 4.2 새 시험

1. **대기열 귀속**: burst 하나가 수십 명령을 가로지르고 늦게 확정돼도 실행 순서·SC·MOpt·LLM·시퀀스 귀속이 섞이지 않는다.
2. **즉시 처리**: setup 실패 직후 학습 시퀀스가 취소되고, timeout 뒤 다음 명령이 발송되지 않는다(지연 회계와 무관하게).
3. **일시정지 실패**: USB 읽기가 멈춘 상태에서 일시정지·PM·종료가 제한 시간 안에 끝나고, 옛 워커와 새 세션이 동시에 핸들을 쓰지 않는다.
   일시정지 timeout 뒤 종료 정리에서도 막힌 `session.close()` 를 다시 부르지 않는다.
4. **무효 범위**: 오류가 명령 사이에 검출되거나 bank 확인에서 뒤늦게 발견돼도 불확실 구간과 겹친 명령들이 무효 처리된다.
5. **구분**: 버퍼 넘침·샘플 0건·관측 실패가 서로 구분되고, idle·백그라운드·명령 집합의 신규 판정이 방식 B 정의와 일치한다.
6. **포착 구간**: 이전 읽기가 시작시킨 값이 경계에 걸치면 명령 보상에서 빠지고, burst 첫 샘플이 앞 명령에 붙지 않는다.
7. **대기열 상한**: 확정 시각이 멈추면 제한 시간 뒤 장애 경로로 가고 해당 명령은 관측 미확정으로 회계된다.
   정상적인 긴 명령(Format 등)은 실행 중에 지연 제한에 걸리지 않고, 완료 뒤 확정이 정체될 때만 제한이 적용된다.
8. **crash flush**: 확정 못 한 명령 목록이 crash 폴더에 남고, 증거 수집이 막히지 않는다.
9. **비교 도구**: v11.2 와 v11.3 기록을 섞으면 측정 방식 차이를 탐지한다.
10. **되돌리기**: `background: false` 면 v11.2.1 과 같은 동작이고, 다른 제품은 영향이 없다.
11. **늦은 포착 모형**: 이전 DRW 호출은 명령 경계 전에 반환됐지만 SBA 포착은 경계 뒤에 일어나는 모형에서, 그 샘플이 앞 명령에 귀속되지 않는다.
    읽기 실패·재핀 뒤 첫 샘플이 이전 트리거 시각을 쓰지 않는다.
12. **burst 전체 무효화**: 여러 명령을 가로지른 오버레이 burst 의 끝 bank 확인이 불일치·실패하면 burst 앞쪽에 걸친 명령까지 모두 관측 실패가 된다.
    - 정상 스왑(두 읽기 성공, 값 다름): 처리 완료 경계는 burst 끝으로 전진하고, 무효 구간이 같은 묶음으로 공개된다.
    - bank 읽기 실패: 정상 검증 경계는 burst 앞에 멈추고, 무효 범위가 직전 정상 검증 경계부터 잡힌다.
13. **늦은 결과**: flush 제한 시간으로 관측 미확정이 된 명령의 검증이 늦게 끝나도 중복 회계·보상이 없고, 대기열·스냅샷 참조가 남지 않는다.
14. **주기 작업 1회**: 실행 수 100 에서 대기 명령 여러 개를 회계해도, 98→103 으로 한 번에 넘어가도 각 주기 작업이 정확히 한 번 돈다.
    state capture 의 시퀀스가 캡처 순간의 명령 이력이다.
15. **판정 자격**: 무효 명령이 먼저 본 BB 를 이후 정상 명령이 밟으면 그 명령이 신규 발견으로 보상받는다(방식 B).
16. **조합 거부**: `background: true` + 예외 주입이면 기동 단계에서 거부된다.
17. **스냅샷 불변**: 스냅샷을 만든 뒤 seed·변이 목록·시퀀스를 바꿔도 지연 회계 결과가 달라지지 않는다.
18. **묶음 공개**: 메인이 샘플·무효 구간·확정 시각의 중간 상태를 읽지 않는다(확정 시각만 앞선 상태로 귀속하지 않는다).
19. **연속 스왑**: 정상 bank 불일치가 연달아 나도 폐기 구간의 대기 명령이 계속 종료되고, 대기열 상한·transport 장애·재연결로 가지 않는다.
20. **같은 코어 연속 burst**: 오버레이가 없는 같은 코어를 연달아 고르고 그 사이에 명령 경계가 있을 때, 다음 burst 첫 샘플(이전 burst 마지막 읽기가 시작시킨 값)이
    다음 명령에 귀속되지 않는다. 주소를 다시 쓴 경우와 이어받은 경우를 둘 다 시험한다.
21. **전송 확인**: errno 거절(양수 rc, NVMe 상태 없음, `_last_cmd_submitted=False`) 명령이 판정 기준 집합을 갱신하지 않는다.

고친 것은 되돌리면 시험이 실패하는지 확인한다(프로젝트 관례).

## 8. 이 계획과 별개 — 후반 exec/s 하락 (2026-10-15 로그로 1차 판정)

처음 가설은 두 가지였다.
(a) 짧은 경로 실패 → 끊을 수 없는 전체 경로 → join timeout → 재연결,
(b) PM 재연결이 점점 비싸짐.
`[Timing]` 실측(§1.1 표)으로 **둘 다 기각**했다.

- (a) 기각: 종료 대기가 초반 0.7ms, 후반 0.3~0.6ms 로 그대로다. join timeout 이 반복됐다면 이 값이 초 단위로 올라갔어야 한다.
- (b) 기각: PM 재연결 1회 평균이 10.29s → 0.79s 로 오히려 줄었다.
- 늘어난 것은 **전송(명령 실행) 하나뿐**이다(7.7ms → 111~116ms). 이 값은 `start_sampling()`(스레드 생성)과 nvme-cli 가 끝날 때까지다.
  샘플링 정지·join 은 들어 있지 않다. 즉 **장치가 명령을 끝내는 데 걸리는 시간**이 늘었다.
- 워커 시간(준비 36.7 + 읽기 64.2ms)이 전송 시간과 비슷한 것은 워커가 명령이 끝날 때까지만 돌기 때문이다. 워커가 명령을 붙잡은 것이 아니다.

남은 후보(로그만으로는 가를 수 없음)

1. **명령 구성 변화** — 후반 corpus·변이·시퀀스가 무거운 명령 쪽으로 쏠림.
2. **장치 상태** — 퍼저가 보낸 Set Features 로 깊은 PS·APST 에 머물러 명령마다 복귀 지연이 붙음. GC·내부 상태 누적.
3. **SBA 트래픽 간섭** — 초반엔 워커가 대부분 준비 단계에서 중단돼 실제 SBA 읽기가 1ms 뿐이었다.
   후반엔 명령 내내 읽는다. 이 읽기가 장치를 느리게 하는지는 분리되지 않았다.

다음 확인

- **느려진 상태에서 전원을 끄지 않고 `--no-jlink` 로 다시 시작**해 `[Timing]` 전송 값을 본다.
  여전히 ~110ms 면 1·2(샘플링 무관), 7~10ms 로 돌아오면 3 이다.
- PS·APST 확인: `grep -E "PS[0-4]|APST|SetFeatures.*(0x02|0x0c)|Power" <로그> | tail -50`
- v11.3 에서 `[Timing]` 에 명령 종류별 전송 평균을 넣어 1 을 직접 본다(§6).

### 10.2 계획과 다르게 구현한 것

1. **회계 함수를 세 단계로 나눴다(§3.2).** 본문은 옮기기만 했고, 창 방식의 `_account_command` 는 세 단계를 같은 순서로 부른다.
   - `_account_exec` — 실행 완료: executions·명령별 실행 수·rc·SC·SC-depth·FWCommit 재연결
   - `_account_coverage` — 커버리지: 새 BB 판정, corpus·det 큐, CSFuzz·MOpt 보상, 학습 관측, ledger, timeout/오류 분기
   - `_account_periodic` — 실행 수 주기 작업: Stats, state capture(장치에 명령을 보낸다), cull, LLM, 그래프

   백그라운드 모드에서 "지연해도 안전한 명령"은 **실행 완료와 주기 작업을 명령이 끝난 즉시** 하고, 커버리지만 대기열에 넣는다.
   대기열의 커버리지 회계는 장치에 접근하지 않는다(시험으로 확인). 그래서 state capture 는 100번째 명령 직후의 장치 상태·명령 이력을
   쓰고, timeout 처리 전에 밀린 회계가 장치 명령을 보내는 일이 없다.
   - 지연 대상: 메인 루프의 단일 명령 중 rc 가 정상이고, 시퀀스·학습 시퀀스·워크로드가 아니며, FWCommit 재연결 대기가 없는 것
   - 나머지(timeout·오류, 시퀀스 멤버, 캘리브레이션, state replay, 워크로드, PM, 시작 단계)는 앞선 대기 명령의 커버리지를 먼저
     회계한 뒤 그 창을 확정해 지금처럼 바로 회계한다(실행 순서 유지).
   - **timeout 은 확정을 기다리지 않는다.** 확정된 대기 명령만 회계하고 나머지는 관측 미확정으로 끝낸 뒤(crash 폴더 목록) 곧바로 crash 처리로 간다.
   - 지연 회계 때 되돌려 놓는 값: 전송 직후의 `_last_nvme_status`·`_last_cmd_submitted`·`_last_wire`·`_credit_seed`·
     `_current_mutations`·`mopt_mode`·학습 송신 기록·창 유효성·예외 플래그, 실행 완료 직후의 `executions`·`_last_depth_adv`
     (corpus `found_at`·ledger `exec`·학습 행이 그 명령 번호를 쓴다). 리스트·dict 는 복사한다.
   - **seed 는 실행 입력을 고정한 사본**(dataclass 복사, learning_meta 깊은 복사, 집합 복사)으로 보관한다. 학습 송신 기록도 그 사본을 가리킨다.
     보상 대상 부모(`_credit_seed`)는 객체 참조다 — 창 방식도 그 객체의 `last_gain_exec` 를 고치고, cull 로 빠진 객체를 고쳐도 해가 없다.
2. **주기 작업(§3.2)**: 실행 완료가 즉시이므로 `% 100` 조건은 실제 완료 수 기준으로 그 명령 직후에 정확히 한 번 참이다(시험 14).
   대기열이 아무리 밀려도 주기 작업이 몰리거나 빠지지 않는다.
3. **crash 미확정 목록(§3.5)**: 로그 WARNING 과 crash 폴더의 `bg_unconfirmed.json`(명령 ID·이름·rc·CDW10·데이터 해시, 최대 200개).
4. **워커 정지 상태의 처리 완료 경계**: 워커가 일시정지·장애 대기·미시작이면 그 전 샘플은 이미 다 공개됐고 앞으로 올 샘플은 재개 뒤에
   포착된다. 이때는 처리 완료 경계를 "지금"으로 본다. 그래서 복구·PM 뒤에 쓸데없이 기다리지 않는다.
5. **동기 확정 때 진행 중 burst 를 끊는다**: 기다리는 시간을 줄이려고 워커에 "끊고 공개" 요청을 보낸다(일시정지와 같은 끊기, 끝 bank 확인은 한다).
6. **응답 없음**: 일시정지 확인이 제한 시간 안에 없으면 `bg_unresponsive`. 그 뒤 `close`·`connect`·`_reconnect`·`reattach`·
   `diagnose` 는 세션에 손대지 않고 실패를 돌려준다. 메인은 복구 없이 캠페인을 멈추고, J-Link·DebugTool 덤프는 건너뛴다.
   `_stop_worker()` 는 워커를 끝내지 않고 일시정지한다.

7. **fresh(직전 값 반복) 판정은 귀속 뒤에** 한다. burst 하나가 명령 경계를 가로지르므로, burst 기준 표시를 그대로 쓰면
   명령의 첫 샘플이 경계 앞(백그라운드·앞 명령) 샘플과 같은 PC 라는 이유로 판정에서 빠진다. 명령·백그라운드로 나눈 관측 안에서
   다시 매긴다. 직전 값은 커버리지 키와 같은 기준인 코어별 **(bank, pc)** 로 비교한다(오버레이는 같은 주소에 다른 코드).
8. **장애 대기 전에는 반드시 무효 구간을 공개**한다. 장애 대기 중이면 메인이 처리 완료 경계를 '지금'으로 보므로(위 4), 그 전에
   직전 정상 검증 경계부터의 무효 구간이 나가 있지 않으면 장애에 걸친 대기 명령이 정상으로 확정된다.

### 10.3 설정

```jsonc
"background": {
  "enabled": false,
  "overlay_burst_len": 64,       // 오버레이 코어 burst 길이(완화책)
  "pending_max": 256,            // 회계를 기다리는 명령 수 상한
  "max_lag_sec": 5.0,            // 명령이 끝난 뒤 처리 완료 경계가 이만큼 못 따라오면 정체
  "pause_timeout_sec": 10.0,     // 일시정지 확인 제한
  "flush_timeout_sec": 10.0,     // 동기 확정·종료 확정 제한
  "queue_max_samples": 100000    // 워커 결과 큐 샘플 상한. 넘으면 메인이 가져갈 때까지 '넘침' 상태 —
                                 //   새 묶음을 쌓지 않고 넘침 묶음 하나의 무효 구간에 합친다(묶음 수 상한 4096도 같다)
}
```

§5 의 "아직 정할 것"은 위 값으로 시작한다. 모두 보수적으로(오탐보다 기다림 쪽으로) 잡았다. 모르는 키·0 이하·숫자 아닌 값은 기동에서 거부한다.
`background` 와 예외 주입을 함께 켜면 기동에서 거부한다(§3.16).

`[Timing]` 줄에 추가된 것: 명령 종류별 전송 평균 상위 3개(§8 의 원인 가르기용), BG 대기 최대·확정 지연 최대·관측 미확정·경계 걸침.
종료 때 `[BG] 요약` 한 줄(지연 회계·동기·미확정·명령 귀속 샘플·경계 걸침·백그라운드·burst·스왑 폐기·장애·넘침).
`run_record` 의 `conditions` 에 `sampling_mode`(window/background)와 `attribution_policy`.

### 10.4 시험 (§4.2 번호)

| §4.2 | 시험 |
|---|---|
| 1·17 | 처리 경계가 3명령씩 늦게 와도 지연 회계 결과(corpus·MOpt·rc·학습·ledger)가 즉시 회계와 같다. 다음 명령이 같은 리스트·dict 를 고쳐도 같다 |
| 2 | timeout 은 지연하지 않고 바로 crash 처리. 그 구간 PC 는 백그라운드만. 대기 명령이 있어도 기다리지 않고 crash 전 장치 명령이 없다 |
| 2 | 확정 전에도 실행 수·rc·SC 가 반영되고 100 경계 주기 작업은 그 명령 직후에 돈다. 지연 회계는 장치·복구·LLM 적용을 부르지 않는다 |
| 3 | 일시정지 확인 뒤 DAP 읽기 없음. 응답 없는 워커는 close·새 워커·재개·재연결 없음, 메인은 복구 없이 중단, 종료 정리에서도 close 안 함 |
| 4 | 전송 실패 → 직전 정상 검증 경계부터 무효, 워커는 세션에 손대지 않고 대기 |
| 5·15 | 백그라운드가 먼저 본 BB 를 명령이 밟으면 그 명령의 신규(방식 B) |
| 6·11 | 포착 구간 = [트리거 직전, 회수 직후]. 경계에 걸친 샘플은 어느 명령에도 안 붙는다 |
| 7 | 정체(완료 뒤 확정 멈춤)·대기 상한 → 관측 미확정 + 장애 경로. 오래된 명령이라도 경계가 따라오면 정체 아님 |
| 8 | 종료 확정이 제한 시간 안에 끝나고 미확정 목록이 crash 폴더에 남는다. `run()` 의 finally 가 보고서보다 먼저 확정한다 |
| 9 | 비교 도구가 window/background 를 섞지 않는다(키 없음 = window) |
| 10 | 꺼짐이 기본, 꺼지면 `RiscvPcsrSampler`, 기존 `burst()` 불변, 다른 샘플러 무관 |
| 12·19 | 여러 명령에 걸친 스왑 폐기 → 그 명령들 관측 실패, 대기열 계속 줄고 장애 아님. 연속 스왑에도 처리 경계 전진 |
| 13 | 정체로 끝낸 명령에 늦게 온 샘플은 중복 회계·보상 없음, 대기열 참조 없음 |
| 14 | 100 경계 작업이 지연 회계가 몰려도·건너뛰어도 정확히 한 번 |
| 16 | 예외 주입과 함께 켜면 기동 거부 |
| 18 | 묶음 단위 공개(워커 묶음 시험들) |
| 20 | 같은 코어 연속 burst·일시정지 뒤 재개의 첫 값은 이전 트리거를 이어받는다 |
| 21 | errno 거절·무효 구간 명령은 판정 집합을 갱신하지 않는다. 실제 문맥(state-replay·calibration·io-workload·fw-preload·startup)도 같고, PM 창만 예외. 소스의 모든 문맥 접두사가 분류돼 있다 |
| 17 | 대기 중 원본 seed 를 바꿔도 corpus·학습에는 보낸 값 |
| 5·15 | 백그라운드 → 명령으로 같은 PC 가 이어져도(stale 표시) 명령의 첫 발견. 같은 burst 안 두 명령이 각자 자기 관측을 받는다 |
| §3.11 | 같은 코어·같은 주소·다른 bank 는 반복이 아니다(명령 창·백그라운드 모두 bank 별 BB 키 유지), 같은 bank 는 반복 |
| 4 | 워커 예외·장애 표시만 세운 경로·재개 직후 장애 모두 무효 구간을 먼저 공개. 예외에 걸친 대기 명령은 보상·학습 근거에서 빠진다 |
| §3.10 | 메인이 안 가져가도 결과 큐의 묶음·무효 구간·샘플 수가 늘지 않는다 |
| — | 끝에서 끝: 진짜 워커 스레드 + 진짜 회계로 40명령. 다른 명령·idle 의 BB 가 섞이지 않는다 |

핵심 조건을 하나씩 되돌리면 해당 시험이 실패하는 것을 확인했다(46가지 + 끝에서 끝 시험의 경계 규칙). 전체 849개(기존 793 + 신규 56) 통과.

### 10.5 실기 전에 알아 둘 것

- 기본은 꺼짐이다. 켜려면 `fuzzer_config.json` 의 BM9K1 `sample_plan.background.enabled` 를 true 로.
- 처음 켤 때 확인할 것은 §7 그대로다. 특히 **같은 조건의 `enabled: false` 와 `[Timing]` 전송 상위 명령의 평균을 비교**해
  상시 SBA 읽기가 명령 시간을 늘리는지(§8-3) 본다.
- `[Timing]` 의 "SBA 준비 · PC 읽기"는 백그라운드 모드에서 워커가 계속 도는 시간이라 명령당 값이 크게 보인다. 명령을 막는 시간이 아니다.
